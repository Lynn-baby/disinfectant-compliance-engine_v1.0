## 六、核心 Insights

### Insight 1: 正清单制对风险判定模型的深远影响

GB 38850-2020 是**正清单（白名单）标准**——只列出"允许使用"的成分，没有"禁止使用"清单。不在清单中的成分 ≠ 禁用，而是"法无明文"。

这直接决定了 S4 的风险判定逻辑：
- S3 定义了 `STATUS_PROHIBITED` 但**从不实际产出**——因为正清单制下没有"禁用"列表
- `unknown` 对应的是 R2（灰色地带），不是 R3（高风险）
- R3 的真正触发路径在**行为信号**（医疗暗示、退单历史、规避监管）而非成分查表
- 未来如果需要真正的 prohibited 检测，需要引入 GB 38850 之外的数据源（如卫生部禁用清单）

### Insight 2: 自动检测优于上游依赖

最初设计时要求 S3 产出 `has_grey_area_ingredients`、S2 产出 `vague_claims` 等标志。但这样做有两个问题：
1. **上游改造风险**：改动已部署的 S2/S3 可能引入回归
2. **职责混乱**：灰色地带判断本质上是风险视角的判定，放在 S4 更内聚

实际方案：S4 自带 `GREY_AREA_PATTERNS`（16 条）和 `VAGUE_CLAIMS_PATTERNS`（14 条），从 `ingredient_name` 和 `target_claims` 自行扫描。好处：
- 不依赖上游升级
- S4 测试可独立覆盖所有检测逻辑
- 规则调整只需要改 S4 一个文件

### Insight 3: 合规引擎的 fallback 方向必须是"紧"不是"松"

两轮审查的核心发现高度一致：**静默失败默认 R1 是最危险的故障模式**。

- JSON 解析失败 → 默认空列表 → R1 → 可以报价（CR-1, SF-3）
- `except Exception` → 全部标志 False → R1 → 可以报价（SF-2）
- `"false"` 字符串 → `bool("false")` 是 True → 误判 R3（SF-1）

修复原则：
- **所有不可恢复的错误 → 保守降级 R3**（禁报价、强制转人工）
- **`_build_error()` 函数专门处理**：统一输出格式 + diagnostics 追踪
- **每处静默默认值都加上 `_warn()`**，确保生产环境可排查

### Insight 4: 两个 Agent 审查发现的问题几乎没有重叠（除了 2 个交叉点）

| 类型 | code-reviewer | silent-failure-hunter |
|------|---------------|----------------------|
| 焦点 | 逻辑正确性、PRD 覆盖、测试缺口 | 静默失败、错误吞噬、fallback 不当 |
| CRITICAL 发现 | 1 个（JSON→R1） | 4 个（bool 字符串 + except 吞噬 + JSON→R1 同 + prohibited） |
| 独有发现 | 模糊宣称误匹配（`"高效液相色谱法"`） | `"false"` 字符串 truthiness、全模块零日志 |

交叉点只有 2 个：JSON 解析失败 → R1、main() 零测试。说明两个 Agent 互补性很强，合在一起覆盖了我手工审核遗漏的 13 个问题。

### Insight 5: KB 过期的含义被重新澄清

原代码 `kb_table_expired and has_unknown` 隐含假设：只有"表过期 + 成分查不到"才升级风险。但 PRD 原则"表过期时 R1→R2 降级，永不放宽"更保守——只要表过期，就说明**整个判定基础可能不可靠**，不管当前能不能查到成分。

修复：`kb_table_expired` 独立检查，全合规产品也降为 R2。但如果已有 R3 触发，不升不降（保守方向正确）。
