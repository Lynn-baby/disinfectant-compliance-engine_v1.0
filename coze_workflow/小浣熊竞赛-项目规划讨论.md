## 二、竞赛策略决策

### 2.1 关键决策：砍掉 S6

**决策**：竞赛版 PRD 砍掉 S6 报价预估，S7 改为轻量 LLM 摘要节点。

**理由**：
- S6 依赖 S5 检测方案稳定后才能做，RICE 排第 12/17
- S6 需要大量定价表数据（每个检测项目 × 客户协议价 × 折扣），数据准备是独立大工程
- 去掉 S6 后，S0-S5 + S7 摘要仍能跑通完整的"安全扫描→解析→分类→合规→风险→检测方案→摘要"链路，演示价值完整
- PRD 6.2 节阶段 1 验收标准就只要求"能用引擎完成一次完整的合规预审对话"，不含报价

### 2.2 S7 策略：LLM 节点而非 Code Node

S7 不需要写代码——在 Coze 中用原生 LLM 节点 + System Prompt，接收 S0-S5 全部输出变量，生成 150 字预审摘要。

优势：
- 零新增代码，零新增测试
- Coze 原生支持，部署 30 分钟
- Prompt 可迭代调整，不需要走"编码→测试→粘贴"循环

### 2.3 辅助项目（法规监控小工具）定位

- 竞赛草案已完成（`法规监控小工具_OPC参赛草案.md`，9 节）
- 作为主项目的**数据保鲜上游**在 PPT 中提及
- 如果时间允许（Day 5+），在 OPC 平台上实现；如果来不及，作为设计文档提交

## 三、第一版计划的形成与反思

### 3.1 第一版计划概要

Plan agent 基于探索结果输出了 5 Phase / ~17.5 小时 / 3-4 天的方案：

```
Phase 1: 竞赛版 PRD 裁剪（2h）
Phase 2: Coze 工作流扩展 — S0/S4/S5/S7 部署（6h）
Phase 3: Coze Bot + KB 上传（1.5h）
Phase 4: 测试 + 截图（2h）
Phase 5: 参赛材料 PPT + 简介（3h）
```

### 3.2 用户对计划的三点质疑

**质疑 1：是否调用专业技能评审过？**
→ 没有。Plan agent 设计方案但不验证可行性。关键假设未核实：Coze Code Node 长度上限、输出变量数量上限、条件节点能力。

**质疑 2：实操落地可能性？**
→ 存在 3 个硬风险未经核实：
- S5 705 行是否超 Coze 限制
- S4 17 个输出变量是否超限制
- Coze LLM 节点能否引用 5 个上游节点的变量

**质疑 3：删减 + 新增后，用户画像精准性？**
→ 用户画像是"一人全栈、单人可落地"。计划中 17.5 小时连续 3-4 天需要确认是否有连续时间块。另外 Coze 实际部署经验存疑。

### 3.3 改进方向：最小粒度方案

核心思想：**把大计划拆成可独立验证的小块，每块做完都有产出，每块之间不互相阻塞**。

对比：

| 维度 | 大粒度计划 | 最小粒度 |
|------|-----------|---------|
| 结构 | 5 个 Phase 线性依赖 | 5 个独立块，每块可单独交付 |
| 风险 | Phase 2 失败 → Phase 3-5 全部卡住 | 某块失败只废该块的时间 |
| 验证 | 最后才测试 | 每块做完立刻验证 |
| 适合 | 前提条件已全部验证 | 前提条件不确定 |

示例拆分：

```
块1: Coze 限制验证（30min）→ 知道能不能放 705 行代码
块2: PRD 裁剪（2h）→ 独立产出，不管部署成不成
块3: 节点逐个部署 + 即时验证（3h）→ S0/S4/S5 逐个确认
块4: Bot + KB + E2E（2h）→ 可演示完整链路
块5: 参赛材料（3h）→ PPT + 简介
```

最极端的小粒度：每天只做一件事，每天有一个可验证结果。
