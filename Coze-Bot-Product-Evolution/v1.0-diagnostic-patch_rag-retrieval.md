# v1.0 诊断补丁：RAG 检索层架构修复

> 触发原因：v1.0 分析报告推荐火山知识库（VikingDB 向量检索），但向量检索=语义检索，无法保证合规场景所需的精确匹配。
> 补丁目标：诊断纯向量检索的具体失效模式，参考法律判例系统方案，调整 v2.0 RAG 层路线图。

---

## 一、法律判例系统调研摘要

### 1.1 北大法宝（最直接可参考的国内系统）

北大法宝 2025 年的 MCP 平台明确将检索拆为**五个独立服务**，互不替代：

| 服务 | 检索方式 | 适用场景 |
|------|---------|---------|
| 检索法律法规-关键词 | 精确匹配 | 已知法规名称/编号 |
| 检索法律法规-语义 | 自然语言语义 | 不确定具体法规名称 |
| 精准查找法条-关键词 | 法规名 + 条号精确查询 | 已知具体法条 |
| 法条识别与溯源 | 文本中提取法规引用 | 文书引用识别 |
| **修正生成幻觉-法条** | **校验 AI 生成的法条内容** | **AI 回答后的法条校验** |

后三项是消字号合规场景直接缺失的能力。尤其是最后一个——**"修正生成幻觉-法条"**——说明法规 AI 领域的共识是：语义检索 + LLM 生成之后，必须再加一层关键词精确校验。

### 1.2 国际法律检索系统的架构共识

Westlaw / LexisNexis / COLIEE 竞赛系统的共同模式——**两级级联管道 (Two-Stage Cascading Pipeline)**：

```
用户查询
  → 查询分类器（Citation-heavy？语义型？）
    → 并行双路检索
      ├── 关键词/符号路：BM25 + Boolean + 字段过滤（精确匹配法规编号、标准号、成分名）
      └── 向量/语义路：Legal-BERT Embedding + ANN（捕捉同义改写、相似案例）
    → 融合层 (RRF / 加权线性组合)
    → 重排序层 (Cross-Encoder / LightGBM LTR)
    → 最终结果 + 置信度分数
```

**关键数据点**：巴西最高法院 (STJ) 的对比实验表明，**BM25 在法规条文的精确匹配上优于纯 Embedding 模型**；Embedding 模型仅在段落级短文本上有优势。COLIEE 2025 的 SIL 框架也证明，BM25 + Doc2Vec 混合特征的 LightGBM 重排序是最高精度方案。

### 1.3 可迁移到消字号合规的三个核心模式

| 法律系统模式 | 消字号合规等价物 |
|-------------|----------------|
| 法条编号精确检索（`《消毒技术规范》第2.1.3条`） | 法规条文/标准号的精确匹配 |
| 判例号/案号精确检索 | 检测标准号精确检索（`GB 15979-2024`） |
| 法宝联想（以法条为纽带关联案例、释义） | 以成分为纽带关联法规条款、检测项目、禁限用清单 |
| 修正生成幻觉 | 生成后校验：输出的法规编号/标准号是否真实存在于知识库 |

## 二、纯向量检索在合规场景下的具体失效模式

以下用 v1.0 知识库中的 4 篇文档为素材，逐一推演失效场景。

### 失效模式 1：检测标准号混淆

```
用户问："GB 15979-2024 和 GB 15979-2002 对消毒湿巾的微生物指标要求有什么不同？"

向量检索实际行为：
  Embedding("GB 15979-2024") ≈ Embedding("GB 15979-2002")
  两个字符串仅末4位不同，Embedding 模型将其映射到几乎相同的向量位置。
  检索结果可能只返回其中一个版本的片段，或两个版本片段混合返回，
  无法区分哪段属于哪个版本。

实际后果：
  LLM 将两个版本的指标交叉引用，输出一个"缝合版"回答——
  部分数据来自2002版，部分来自2024版，用户抄去备案，直接被退。
```

### 失效模式 2：法规条文号跳位

```
用户问："《消毒产品卫生安全评价规定》第十四条对产品责任单位有什么要求？"

向量检索实际行为：
  知识库中"第十四条"的内容和"第十三条""第十五条"在语义上高度相似
  （都在讲责任单位的义务），向量检索可能把 Top-3 片段分别返回
  第十三条、第十四条、第十六条的内容，唯独漏了第十四条本身。

实际后果：
  LLM 基于十三条和十六条推理出"第十四条的要求"，编造了不存在的条文内容。
  这在 v1.0 的纯 Prompt 约束下根本无法拦截——因为 Prompt 只禁止编造价格/周期，
  没禁止编造条文内容（3.5节也仅列出"法规编号"）。
```

### 失效模式 3：成分名称的"近似灾难"

```
用户问："聚六亚甲基双胍盐酸盐可以用于免洗手消毒液吗？"

向量检索实际行为：
  "聚六亚甲基双胍盐酸盐" 和 "聚六亚甲基胍盐酸盐" 和 "聚六亚甲基双胍"
  是三种不同的化学物质，但在 Embedding 向量空间中距离极近。
  向量检索可能返回"聚六亚甲基胍"的法规信息，LLM 把它当成"双胍"的答案。

实际后果：
  "聚六亚甲基胍"可能不在禁用清单但"双胍盐酸盐"在——检索错了，结论全错。
  用户按合规结论投产 → 实际违规 → 商业事故。
```

### 失效模式 4：跨文档语义漂移

```
用户问："抑菌洗手液需要做哪些毒理学检测？"

向量检索实际行为：
  "抑菌洗手液"语义上接近"抗抑菌制剂"（在文档01_备案可行性判断中），
  也接近"消毒剂检测"（在文档02_检测项目与报价中），
  还接近"卫生许可"（在文档03_备案流程与资料中）。
  
  Top-5 片段可能来自3篇不同文档，但"毒理学检测"这个精确需求可能只
  出现在文档02的某个分片中——而这个分片可能因为语义不够接近被排到第8名以外。

实际后果：
  LLM 接收到的上下文是备案流程+产品分类，但缺了核心的毒理学检测清单。
  LLM 于是"合理推测"检测项目——这就是典型的 RAG 幻觉。
```

### 失效模式 5：禁限用清单的二元判定失败

```
用户问："三氯生能在消毒产品中使用吗？"

正确行为：
  这是一个需要精确二值回答的问题（能/不能/有条件使用）。
  应该查询结构化黑名单/白名单，找到"三氯生"的确切法规状态。

向量检索实际行为：
  返回"三氯生"相关片段 + "其他禁用成分"相关片段，混在一起。
  LLM 可能从"三氯生曾广泛用于抗菌产品"的上下文推断"可以用"，
  但实际上三氯生在特定品类中已被限制。

实际后果：
  这是所有失效模式中最危险的——涉及安全底线的问题，不能用语义近似来回答。
  向量检索的"模糊性"在这里是致命缺陷。
```

### 失效模式汇总

| 失效类型 | 根因 | 影响等级 | 向量检索为什么不行 |
|---------|------|---------|-------------------|
| 标准号混淆 | Embedding 对结构化编号的区分力弱 | 高 | 编号仅末几位不同，向量距离极小 |
| 条文号跳位 | 相邻条文语义高度相似 | 极高 | Top-K 语义排序 ≠ 条文号排序 |
| 成分名称近似 | 化学名称的字符级差异在语义空间中不可见 | 极高 | Embedding 捕获语义不捕获字符 |
| 跨文档漂移 | 多文档主题重叠，精确片段被淹没 | 高 | 无结构化字段过滤，纯靠语义排序 |
| 二元判定失败 | 禁限用清单需要精确匹配而非语义理解 | 极高 | 向量检索本质是排序，不是判定 |

## 三、v2.0 路线图调整方案

### 3.1 原路线图的问题

原报告 v2.0 路线图将 RAG 工作放在**阶段 2（工程化）**，仅列为：

> 任务 11：实现知识库优先级调用规则 | 高
> 任务 14：RAG 检索效果测试（召回率/准确率）| 高

问题在于：**RAG 检索架构是基础设施，不是"优化项"**。如果检索层在阶段 1 就被默认设为纯向量检索，阶段 1 的所有工作（状态机、Prompt、风险分级）都建立在"检索结果是正确的"这个错误前提上。正确的检索结果应该是 Phase 1 的前置条件，不能等到 Phase 2 再去"测试召回率"。

### 3.2 调整后的路线图

**阶段 0：检索基础设施重构（先于原阶段 1，1 周）**

| 序号 | 任务 | 优先级 |
|------|------|--------|
| R0 | 搭建混合检索引擎（BM25关键词 + 向量语义，双路并行） | 极高 |
| R1 | 建立结构化成分数据库（白名单/黑名单/限制清单，不走向量检索） | 极高 |
| R2 | 建立检测标准号-版本索引（精确匹配用） | 极高 |
| R3 | 定义查询分类规则（成分查询→关键词；泛化咨询→向量；法规编号→精确匹配） | 极高 |
| R4 | 实现检索结果的可溯源引用机制（每条回答标注来源文档+分片ID） | 高 |

**阶段 1：基础重构（原路线图保持不变，但建立在混合检索之上）**

**阶段 2：工程化（增加检索质量门禁）**

| 序号 | 调整 |
|------|------|
| 原任务 11 | 从"知识库优先级调用规则"升级为"混合检索 + 查询路由 + 重排序" |
| 原任务 14 | 从"RAG检索效果测试"升级为"分查询类型的召回率/精确率评测（法规编号类/成分类/泛化类分别评测）" |
| 新增 R5 | 实现生成后的法规编号/标准号校验（参考北大法宝"修正生成幻觉"服务） |
| 新增 R6 | 实现结构化成分数据库的定期更新机制 |

### 3.3 路线图对比

| | 原 v2.0 | 调整后 v2.0 |
|------|---------|------------|
| RAG 定位 | 阶段 2 工程化项 | **阶段 0 基础设施** |
| 检索方式 | 单一向量检索（VikingDB） | 混合检索（BM25 + 向量 + 结构化查询） |
| 成分合规 | 全走知识库语义检索 | **结构化白名单/黑名单数据库**，不走 LLM |
| 标准号/条文号 | 靠向量检索召回 | **精确关键词索引** ± 向量兜底 |
| 幻觉校验 | Prompt 约束 | Prompt + **检索后校验**（生成内容 vs. KB 原文） |
| 评测方式 | 笼统的"召回率/准确率" | **分查询类型的分别评测** |

## 四、具体落地架构

### 4.1 推荐混合检索架构（可运行在 Coze 外部）

Coze 内置的 VikingDB 只支持向量检索，无法直接实现混合检索。建议架构：

```
┌─────────────────────────────────────────────────────┐
│                    Coze Bot 层                       │
│  System Prompt / 状态机 / 变量采集 / 风险分级        │
│  （原 v2.0 阶段 1 的全部工作）                       │
└────────────────────────┬────────────────────────────┘
                         │ Function Calling
                         ▼
┌─────────────────────────────────────────────────────┐
│              Coze Workflow / 外部 API                │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │          查询分类器 (Query Router)            │   │
│  │  ├── 含标准号/法规编号 → 精确关键词检索        │   │
│  │  ├── 含成分名称       → 结构化数据库查询       │   │
│  │  └── 泛化合规咨询     → 混合检索               │   │
│  └─────────────────────────────────────────────┘   │
│                         │                           │
│         ┌───────────────┼───────────────┐           │
│         ▼               ▼               ▼           │
│  ┌──────────┐  ┌──────────────┐  ┌──────────┐      │
│  │ 精确检索 │  │ 结构化数据库 │  │ 混合检索 │      │
│  │──────────│  │──────────────│  │──────────│      │
│  │Elastic-  │  │ PostgreSQL   │  │ BM25 +   │      │
│  │search    │  │ / SQLite     │  │ 向量双路 │      │

│  │Boolean   │  │ 禁限用清单   │  │ 融合     │      │
│  │精确匹配  │  │ 检测标准对照 │  │          │      │
│  └──────────┘  └──────────────┘  └──────────┘      │
│         │               │               │           │
│         └───────────────┼───────────────┘           │
│                         ▼                           │
│              ┌──────────────────┐                   │

│              │  · 法规编号校验  │                   │
│              │  · 成分状态标记  │                   │
│              └──────────────────┘                   │
└─────────────────────────────────────────────────────┘
```

### 4.2 三类查询的精确检索策略

**A. 成分相关查询 → 结构化数据库（不走语义检索，不走 LLM 自由生成）**

```
数据模型：
  ingredients
  ├── id
  ├── name_cn (精确名称)
  ├── aliases (别名数组，如 ["PHMB", "聚六亚甲基双胍"])
  ├── cas_number
  ├── status: 'allowed' | 'restricted' | 'prohibited'
  ├── restriction_detail (如 "限用于非接触皮肤的硬表面消毒")
  ├── regulation_ref (如 "《消毒技术规范》2002版 第2.1.3条")
  ├── allowed_categories (适用品类)
  └── last_updated

查询逻辑：
  - 精确名称匹配（LIKE 或全文索引，不做模糊）
  - 别名匹配（数组包含查询）
  - 未命中 → 走混合检索兜底 + 标记"需人工确认"
  - LLM 仅负责把查询结果用自然语言包装，不负责"判断"成分合规状态
```

`★ Insight ─────────────────────────────────────`
**为什么成分合规不能进 LLM：**
成分合规是二值判定（能用/不能用/有条件使用），不需要 LLM 的"理解"和"推理"能力。
LLM 在这里是风险源，不是能力源。正确做法是：
- 数据库做判定（确定性）
- LLM 做表述（把 `status: prohibited` 翻译成"该成分在消字号产品中禁止使用，依据《XXX》第X条"）
- 数据库没查到 → 不猜，直接说"需人工确认"

这对应北大法宝的"修正生成幻觉-法条"服务——AI 回答了法条内容后，再用精确匹配校验回答中的法条是否真实存在于数据库。
`─────────────────────────────────────────────────`

**B. 法规编号/标准号查询 → 精确关键词检索**

```
索引策略（以 Elasticsearch 为例）：
  - 对标准号字段使用 keyword 类型（不做分词，精确匹配）
  - 对条文号使用专用字段索引（如 article_number: "第十四条"）
  - 对法规标题使用 standard 分词器（中文分词 + 精确匹配双索引）

查询路由规则：
  if query matches pattern "GB/T?\s*\d+[.-]\d+"     → 精确标准号查询
  if query matches pattern "第[一二三四五六七八九十百]+条" → 精确条文号查询
  if query matches pattern "《.+》"                   → 精确法规标题查询
  else                                                → 混合检索

兜底策略：
  精确检索未命中时，不自动降级为向量检索。
  而是明确告知："当前知识库中未检索到该法规/标准号的原文，请核实编号是否正确。"
  避免向量检索"搜到一条近似的就当正确的返回"。
```

**C. 泛化合规咨询 → 混合检索 (BM25 + 向量 + RRF 融合)**

```
流程：
  1. 用户查询 → 同时发往 BM25 关键词索引和向量语义索引
  2. 两路各返回 Top-15
  3. RRF (Reciprocal Rank Fusion) 融合排序
  4. 对 Top-10 用轻量 Cross-Encoder 重排序
  5. 返回 Top-5 片段 + 每个片段标注来源文档和分片位置
  6. LLM 基于这些片段生成回答，不超出片段范围

为什么需要 BM25 而不只靠向量：
  - "消毒产品备案材料清单"中"备案"和"材料"是精确关键词
  - 向量检索可能因为语义扩展把"备案"扩展到"行政审批"、"许可证"等
  - BM25 的词汇精确匹配能保证"备案材料"这个词本身不出现在无关文档中时不会被召回
```

### 4.3 生成后校验层（最关键的新增模块）

参考北大法宝的"修正生成幻觉-法条"服务：

```
LLM 生成回答
  → 正则提取回答中所有法规/标准引用：
    - 标准号模式：GB/T?\s*\d+[.-]\d+
    - 法规书名号：《.+》
    - 条文号模式：第[一二三四五六七八九十百]+条
  → 逐一在精确索引中校验：
    - 存在且版本正确 → 标注 ✅
    - 存在但版本错误 → 标注 ⚠️ 并替换为正确版本
    - 不存在 → 标注 ❌ 拦截，禁止输出，重新生成
  → 输出最终回答 + 溯源引用列表
```

这是向量检索之外的一层**独立安全网**——即使检索和生成都出错了，校验层仍能拦截。

### 4.4 技术选型对照（Coze 内 vs. Coze 外）

| 模块 | Coze 内可实现 | 需 Coze 外补充 | 推荐方案 |
|------|-------------|---------------|---------|
| BM25 关键词检索 | Workflow 调用外部 API | Elasticsearch / Meilisearch | Meilisearch（轻量，单人可维护） |
| 向量语义检索 | VikingDB（内置） | — | 保留 VikingDB 做语义路 |
| 结构化成分数据库 | Workflow 调用外部 API | PostgreSQL / SQLite | SQLite（4篇KB量级，JSON文件都够） |
| 查询分类器 | Workflow 代码节点 | — | Coze 代码节点写路由规则 |
| RRF 融合排序 | Workflow 代码节点 | — | Coze 代码节点实现 |

## 五、总结：原报告的核心遗漏

原 v1.0 报告的诊断方向是正确的——状态机、结构化采集、风险分级确实是核心缺口。但它漏了一个更底层的问题：

> **RAG 检索质量是所有上层架构的地基。如果检索层返回了错误/不完整的法规信息，状态机再严谨、风险分级再精细、Prompt 再严格，都是在错误信息上做正确推理——结论仍然错误。**

具体来说，原报告有三个 RCA（根因分析）级别的遗漏：

| 遗漏 | 说明 |
|------|------|
| 未区分"检索"和"生成"两个独立的风险源 | 报告把所有幻觉问题归为 Prompt 约束不足，但检索层本身就会引入错误信息 |
| 未质疑向量检索是否适合合规场景 | 默认接受了"知识库 = 向量检索"的前提，没有挑战这一前提 |
| 未参考法律/法规领域的检索最佳实践 | 北大法宝的"关键词+语义"双模、"修正生成幻觉"等模式完全可以直接迁移 |
