## 1. 产品概述

### 1.1 产品定位

**消字号合规预审引擎**（以下简称「引擎」）是一套面向第三方检测机构的 AI 预审系统。输入产品信息，自动完成品类判定、成分合规检查、风险分级、检测方案推荐和报价区间预估，将售前咨询从「人工经验驱动」升级为「系统规则驱动」。

与上一版 Bot 的本质差异：前者是「法规问答机器人」，本引擎是「合规预审决策系统」。核心能力不是聊天，而是按照固定规则对输入信息做出可靠的结构化判定。

### 1.2 核心价值

| 价值维度 | 具体表现 |
|---------|---------|
| 提升接单速度 | 销售拿到客户产品信息后，2 分钟内输出检测清单和报价区间，不再翻资料或等老人回复 |
| 降低退单风险 | 在接单前识别出 R3 高风险产品，避免投入资源后备案被拒 |
| 标准化新人能力 | 新销售/新备案经理不再依赖师傅带教，独立完成预审 |
| 数据可沉淀 | 每次预审产生结构化记录，可分析高频成分、风险分布、客户质量 |

### 1.3 成功指标

| 指标 | 目标值 | 衡量方式 |
|------|--------|---------|
| 预审完成率 | 进入流程后完整走完 S4（风险评级）的会话 ≥ 60% | 状态机到达率 |
| 信息采集完整率 | 6 个必采字段全部填充的会话 ≥ 80% | 变量填充率 |
| 风险判定准确率 | 与人工审核对比 ≥ 90% | 抽检 50 条预审记录 |
| 知识库引用率 | 合规类判定中引用知识库的比例 ≥ 70% | 检索命中统计 |
| 输出结构一致性 | 100% 按模板输出 | 结构校验 |
| 自动处理率 | 无需转人工即可完成完整预审的会话 ≥ 50% | 转人工率反向计算 |

## 2. 用户分析

### 2.1 目标用户画像

| 角色 | 典型需求 | 核心痛点 |
|------|---------|---------|
| **第三方检测机构 — 销售工程师** | 客户询价时快速判断检测项目和报价，抢占接单先机 | 输入产品信息 → 秒出检测清单和报价区间。当前靠个人经验翻内部资料，新人无法独立接客 |
| **第三方检测机构 — 备案经理** | 接手备案项目后评估合规风险和材料缺口 | 批量快速初筛，退单风险前置识别。当前靠人工逐份审核，效率低且标准不一致 |
| **品牌方产品经理** | 新品上市前确认合规路径 | 快速知道能不能做、要花多少钱、多久。当前信息不对称，只能人脉打听 |
| **代工厂技术负责人** | 客户来单后判断能不能接 | 成分是否合法、检测项目清单。当前依赖有经验的技术人员，人员离职风险高 |

### 2.2 用户痛点（四要素分析）

1. **销售工程师 / 接单报价** — 客户微信发来成分表询价，需要判断属于哪类消毒产品、需要哪些检测项目、多少钱、多少天。当前依赖个人经验翻内部资料，响应慢且容易漏项，新人更是无从下手。在竞对林立的检测市场中，谁能先给出专业报价谁就能抢到单。

2. **备案经理 / 项目预审** — 手上有多个项目排队，需要评估每个产品的成分是否合规、功效宣传是否踩线、现有材料是否齐全。当前靠人工逐份审核，效率低且依赖个人经验，退单风险难以标准化评估。理想状态是「批量输入 → 自动初筛 → 只对高风险的做人工复核」。

3. **品牌方 / 新品上市** — 不知道自己的产品成分能不能做消字号备案，市面上咨询机构报价不透明，周期不确定。当前只能靠人脉打听或找多家机构比价，决策成本高。

4. **代工厂 / 接单判断** — 客户发来产品配方，需要快速判断能不能接单、会不会有法规风险。当前依赖有经验的技术人员人工判断，人员离职风险高，新人培养周期长。

### 2.3 核心用户场景

**场景 A：销售接单 — 2 分钟报价抢单**
> 销售小王收到客户微信："帮我看看这个洗手液能不能做消字号备案，成分表发你了"。小王打开引擎，粘贴成分信息。系统自动判定产品属于第二类（抗抑菌制剂），列出检测项目清单，给出费用区间和参考周期。小王 2 分钟内回复客户，比竞对快了半天，拿下订单。

**场景 B：备案经理 — 批量项目初筛**
> 备案经理老李手上有 5 个新项目等着排期。他用引擎逐一输入产品信息，引擎对每个项目输出风险等级和材料缺口清单。其中 1 个产品触发 R3 高风险（含禁用成分），老李直接告知客户无法备案。另外 4 个产品按 R1/R2 分类，他优先处理 R2 的 2 个，把 R1 的分给新人跟进。

**场景 C：品牌方自检 — 新品合规预判**
> 品牌方产品经理小张拿到一个新配方，想知道能不能做消字号备案。他打开引擎，输入产品类型、剂型、成分。引擎输出风险等级和建议检测项目。小张带着这份预审报告去找检测机构谈合作，不再空手砍价。

## 3. 产品架构

### 3.1 系统分层

```

└──────────────────────────────────────────────┘
                      │
┌──────────────────────────────────────────────┐
│             判定引擎层                         │
│  ┌────────────┐ ┌────────────┐ ┌──────────┐  │
│  │ 产品分类器 │ │ 成分合规   │ │ 风险分级 │  │
│  │ Classifier │ │ 检查器     │ │ 引擎     │  │
│  └────────────┘ └────────────┘ └──────────┘  │
│  ┌────────────┐ ┌────────────┐               │

│  法规知识库 (VikingDB) │ 会话记录 │ 规则配置    │
└──────────────────────────────────────────────┘
```

### 3.2 架构原则

1. **判定先行，对话为辅** — 引擎的核心价值是「做出准确的合规判定」，聊天界面只是信息采集的通道。任何时候，能力投入优先级：判定规则 > 对话体验。
2. **不安全就不输出** — 当信息不完整或知识库无依据时，引擎有义务拒绝输出结论并解释原因，而不是给出一个「可能的」答案。
3. **每个判定可追溯** — 合规结论必须附带依据来源（知识库引用 / 规则编号），没有依据的结论等同于错误结论。

### 3.3 核心模块说明

| 模块 | 职责 | 输入 | 输出 | 判定方式 |
|------|------|------|------|---------|
| **状态机引擎** | 控制对话流转，信息采集完整后才进入判定 | 用户输入 + 当前状态 + 变量状态 | 下一状态 + 动作指令 | Code Node 查迁移规则表 |
| **产品分类器** | 判定产品类别和适用法规路径 | product_name + target_claims + dosage_form | 品类标签 + sub_type + 法规依据 + 匹配关键词 | Code Node 5步决策树（Phase0命名校验 + Step1-4关键词匹配 + 子类型冲突检测），不进LLM |

**产品三分类**（依据《消毒产品分类目录》）：

| 类别 | 风险程度 | 管理要求 | 涵盖范围 |
|------|---------|---------|---------|
| **第一类** | 较高风险 | 严格管理 | 用于医疗器械的高水平消毒剂和消毒器械、灭菌剂和灭菌器械，皮肤黏膜消毒剂，生物指示物、灭菌效果化学指示物 |
| **第二类** | 中度风险 | 加强管理 | 除第一类产品外的消毒剂、消毒器械、化学指示物，以及带有灭菌标识的灭菌物品包装物、抗（抑）菌制剂 |
| **第三类** | 较低风险 | 常规管理 | 除抗（抑）菌制剂外的卫生用品 |

#### 3.3.0 产品分类判定规则（Code Node 硬编码，不进 LLM）

分类逻辑为 5 步决策树：Phase 0 命名规范前置校验（禁用词/外文字母/三段式校验）+ Step 1-4 关键词分类逻辑 + 子类型冲突检测（resolve_conflict）。Code Node 硬编码执行，不进 LLM。全部数据（关键词、禁用词、属性名后缀）硬编码在 Code Node 中，零外部依赖。

**输入**: product_name + target_claims + dosage_form（来自 S1 入口解析）

##### Phase 0：命名规范前置校验（卫生部《健康相关产品命名规定》）

在关键词分类之前，先校验产品名称是否符合命名规范。不合规名称直接拦截，避免被误分到某个品类。

| 校验项 | 规则 | 依据 |
|--------|------|------|
| 禁用词检测 | 不得含"特效/高效/广谱/第一代/最强/顶级/100%/绝对"等绝对化词语 | 第八条 |
| 外文字母检测 | 不得含外文字母（注册商标除外），检测连续 2+ 个 ASCII 字母 | 第八条 |
| 三段式结构 | 名称须为「商标名+通用名+属性名」三段式，缺一不可 | 第四条 |
| 属性名后缀 | 名称须以已知属性名结尾（泡腾片/洗手液/喷雾/凝胶/湿巾/洗液/液/片/粉/膏/乳/霜/皂/巾/剂/水等） | 第五条第三款 |
| 功能性开头 | 名称以"消毒/抗菌/抑菌/杀菌/灭菌/医用/医疗/一次性/卫生/清洁"开头 → 缺商标名 | 第四条 |
| 占位符/过短 | 名称 ≤2 字或为"新产品/样品/测试/未知/待定/未命名/新品" | 第四条 |

未通过 Phase 0 → 直接返回"未分类"，附带具体修正提示，不进入关键词匹配。

```
  │   "消毒喷雾", "消毒液", "消毒剂", "消毒片", "消毒粉",        │
  │   "杀菌", "杀灭率", "灭活", "杀灭", "消毒"                   │
  │                                                             │
  │ 抗（抑）菌制剂关键词:                                       │
  │   "抗菌制剂", "抑菌制剂", "抗（抑）菌", "抗抑菌",            │
  │   "抗菌洗液", "抑菌洗手液", "抗菌洗手液",                    │
  │   "抗菌喷雾", "抑菌喷雾", "抗菌凝胶", "抑菌凝胶",            │
  │   "抗菌", "抑菌"                                            │
  │                                                             │
  │ 命中（无冲突）→ 返回 第二类 + sub_type                      │
  │ 命中（有冲突）→ 返回 第二类 + needs_review=True              │
  │ 未命中 → Step 3                                             │
  └─────────────────────────────────────────────────────────────┘

Step 3 — 卫生用品关键词命中 → 第三类
  ┌─────────────────────────────────────────────────────────────┐
  │ 搜索 product_name + target_claims。                         │
  │                                                             │
  │ 关键词:                                                     │
  │   "卫生巾", "卫生护垫", "纸尿裤", "纸尿片", "尿不湿",        │
  │   "湿巾", "卫生湿巾", "纸巾", "棉柔巾", "洗脸巾",            │
  │   "化妆棉", "棉签", "棉棒", "口罩", "手套",                  │
  │   "一次性", "卫生用品"                                       │
  │                                                             │
  │ 命中 → 返回 第三类（sub_type=卫生用品）                      │
  │ 未命中 → Step 4                                             │
  └─────────────────────────────────────────────────────────────┘

Step 4 — 兜底: 剂型辅助判断
  ┌─────────────────────────────────────────────────────────────┐
  │ 如果剂型 = 湿巾 且 前几步未命中 → 第三类卫生用品              │
  │                                                             │
  │ 如果所有关键词均未命中且剂型无法辅助 → 返回 未分类           │
  │ needs_review=True，提示转人工确认                            │
  └─────────────────────────────────────────────────────────────┘
```

**为什么这样设计**：
- Phase 0 命名校验在关键词分类之前执行：不合规的名称不应进入分类流程，避免被误分到某个品类
- Step 1 仅搜索 product_name：第一类是高风险产品，必须通过产品名称本身判定，不能因宣称功效中含某个词就升级风险等级
- Step 1 移除"口腔/牙科/眼科/妇科"裸词（2026-05-26 审计 #1 致命）：裸词会错误拦截普通口腔清洁/消毒产品。只有用于口腔黏膜消毒的产品才属于第一类
- Step 2 合并消毒剂/消毒器械/抗抑菌制剂为同一判定层（2026-05-26 审计 #2 致命）：三者同属第二类但检测方案不同。子类型冲突通过 resolve_conflict 检测并转人工，不能靠 Step 顺序消解——宣称"消毒"的产品应按消毒剂管理，不因同时宣称"抑菌"而降级为抗抑菌制剂
- 关键词按长度降序匹配：长词优先（如"消毒器械"先于"消毒"），避免短词抢先命中导致子类型误判
- 未分类不推断：宁可转人工，不能分错类
- 关键词列表是封闭集合，新增只需追加列表，不改逻辑代码

**关键约束**：
- 消毒剂和抗抑菌制剂同属第二类，但检测方案不同（杀菌试验 vs 抑菌试验），分类后需通过 sub_type 区分
- resolve_conflict 检测到消毒剂+抗抑菌制剂同时命中 → needs_review=True 转人工，禁止在 Code Node 内靠优先级消解
- 第一类的皮肤黏膜消毒剂和用于医疗器械的消毒剂在 S3（成分合规）和 S5（检测方案）上的要求不同，暂不区分子类
- 分类不依赖 usage_scenarios（选采字段），仅依赖 product_name + target_claims + dosage_form

#### 3.3.0.2 成分合规检查规则（Code Node 硬编码，不进 LLM）

成分合规检查基于 GB 38850-2020《消毒剂原料清单及禁限用物质》（含第 1 号修改单）硬编码查表。Code Node 执行，不进 LLM。

**输入**: main_ingredients + product_category + sub_type（来自 S1 入口解析 + S2 分类判定）

##### 数据架构：三层查表体系

```
第 1 层 — GB 38850-2020 表1：活性（有效）成分清单（85 项）
  格式: "归一化名称": (CAS编码, 使用范围代码, [常用别名])
  使用范围代码: A=室内空气 C=污染物 D=生活饮用水 E=环境及物体表面
              H=人体 K=集中空调 M=医疗器械 S=游泳池水 W=医院污水
              #E=仅限于物体表面

第 2 层 — GB 38850-2020 表2：惰性成分清单（115 项）
  格式: "归一化名称": (CAS编码, 使用范围代码, [常用别名])

第 3 层 — 市场俗名映射（MARKET_ALIASES，9 条，人工维护）
  用户实际会输入但不在 GB 38850 标准名称中的常用名
  映射关系（人工维护，脚本不覆盖）：
    "酒精"   → "乙醇"
    "双氧水" → "过氧化氢"
    "甘油"   → "丙三醇"
    "纳米银" → "银离子"
    "碘伏"   → "聚维酮碘"
    "84消毒液" → "次氯酸钠"
    "新洁尔灭" → "苯扎溴铵"
    "洗必泰"  → "醋酸氯己定"
    "卡波姆"  → "聚丙烯酸"
```

##### 成分状态枚举（5 种）

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `allowed_active` | 在活性成分清单中 | 命中表1（活性成分） |
| `allowed_inert` | 在惰性成分清单中 | 命中表2（惰性成分） |
| `restricted` | 限用物质（需检查浓度） | 命中表1/表2但受第6条限量约束 |
| `unknown` | 未在任何清单中命中 | 表1和表2均无匹配 |
| `water_base` | 水/溶剂基底 | 成分名为水/去离子水/纯水等 |

> **注意**: S3 定义了 `STATUS_PROHIBITED` 但实际不产出——GB 38850-2020 是正清单制，不在清单中 = unknown 而非 prohibited。真正的禁用物质判定（如含抗生素、激素等药品成分）依赖 KB 药典数据，在 Code Node 中以 `PROHIBITED_SIGNALS` 关键词列表做信号检测。

##### 成分匹配策略（三级递进）

```
Step 1 — 精确匹配一级索引
  输入成分名归一化后直接查 LOOKUP 索引（含标准名+别名+市场俗名）
  命中 → 返回 allowed_active / allowed_inert
  未命中 → Step 2

Step 2 — 模糊子串匹配
  遍历 LOOKUP 中所有 key，检查是否与输入成分名互相包含
  命中 → 返回 allowed_active / allowed_inert（标注"近似匹配至"）
  未命中 → Step 3

Step 3 — 未收录
  返回 unknown
  提示可能原因：
    1) 属于新消毒产品原料，需按《新消毒产品和新涉水产品卫生行政许可管理规定》办理
    2) 名称使用了非标准表述，请核实 INCI 名称或 CAS 号后重新查询
```

**归一化预处理**:
- 剥离浓度后缀：`乙醇（75%）` → `乙醇`
- 剥离含量描述：移除含"含量/浓度/纯度"的括号内容
- 剥离比较符后缀：`≤0.5%` 等
- 浓度提取：支持 `%`、`g/L`、`mg/L` 后缀，单独解析为 conc+unit 字段

##### 限用限量检查（GB 38850-2020 第6条）

5 种限用物质，分 skin（皮肤消毒）和 mucosal（黏膜消毒）两档限量：

| 物质 | 皮肤限量 (6.1) | 黏膜限量 (6.2) |
|------|---------------|---------------|
| 葡萄糖酸氯己定 | ≤45 g/L | ≤5 g/L |
| 醋酸氯己定 | ≤45 g/L | ≤5 g/L |
| 三氯生 | ≤20 g/L | ≤3.5 g/L |
| 苯扎溴铵 | ≤5 g/L | ≤2 g/L |
| 苯扎氯铵 | ≤5 g/L | ≤2 g/L |

**限量判定逻辑**:
1. 匹配到受限物质 → 状态标记为 `restricted`
2. 如用户提供了浓度 → 尝试判断是否超标
   - `%` 浓度近似换算：1% ≈ 10 g/L
   - `mg/L` → 除以 1000 转为 g/L
3. 超标标记 `exceeded: true` 但仅在 basis 中提示，不自动阻断——最终判定权留给 S4 风险分级

##### 总体状态判定

```
check_compliance() 汇总所有成分结果后输出 overall_status:

  所有成分均在清单中（含 water_base） → all_allowed
  含 restricted 成分（无 unknown）     → has_restricted
  含 unknown 成分（非全部）            → has_unknown
  全部成分均为 unknown                → all_unknown
  未提供成分信息                      → no_ingredients
```

**为什么这样设计**:
- 硬编码查表而非 KB 检索：GB 38850-2020 清单是国标固定集合，改动频率极低（截止 2026-05 仅 1 次修改单）。硬编码消除检索延迟和误匹配，确保每次判定结果完全一致
- 市场俗名映射独立维护：9 条俗名是实践中高频出现的非标准名称，单独一个字典管理，不混入标准数据提取流程
- 模糊匹配放在精确匹配之后：先精确后模糊，避免"乙酸"误匹配"乙二胺四乙酸二钠"
- `%` → `g/L` 换算为近似值（1%≈10 g/L）：精确换算需要密度数据，当前保守取近似。限用物质接近临界值时建议人工复核
- unknown 不推断为 prohibited：正清单制下"法无明文"是灰色地带而非违规。合规底线由 S4 风险分级负责（unknown → 至少 R2）

**与 S4 风险分级的接口**:
- S3 输出 5 种状态 → S4 通过 `_normalize_status()` 映射为 3 种（allowed/restricted/unknown）
- restricted 成分在风险层面视为 allowed（在标准内），但保留 restricted_count 独立计数
- unknown 成分触发 S4 灰色地带自动检测（`GREY_AREA_PATTERNS` 16 条关键词扫描）

| **成分合规检查器** | 逐成分查 GB 38850-2020 清单判定合规状态，含限用限量检查 | 成分列表 + product_category + sub_type | allowed_active / allowed_inert / restricted / unknown / water_base + CAS + 法规依据 + 限量检查结果 | Code Node 硬编码查表（85项活性+115项惰性+5项限用限量+9条市场俗名映射），不进LLM |
| **风险分级引擎** | 综合多个维度输出风险等级 | 成分结果 + 功效宣传 + 产地 + 退单历史 | R1 / R2 / R3 + 触发条件列表 | Code Node 查表（伪代码见 3.4） |
| **检测方案生成器** | 生成检测项目清单 | 品类 + 功效宣传 + 剂型 | 检测项目清单（项目名称 + 参考标准 + 依据来源） | Code Node 查表为主，非标准宣称 LLM 介入（见 3.3.1） |
| **报价预估器** | 给出价格区间和参考周期 | 检测清单 + urgency | 价格区间 + 参考周期 + 报价依据 | Code Node 查表为主，仅异常项 LLM 评估（见 3.3.2） |

#### 3.3.1 检测方案生成器（S5）执行逻辑

LLM 不可能凭空知道「洗手液+抑菌」需要测什么。检测方案的生成逻辑是查表，不是推理。表存在知识库里，Code Node 读表执行。

```
输入: product_category + target_claims + dosage_form
  │
  ▼
Step A — Code Node: 查「品类 × 剂型 → 基础检测包」映射表
  │  （表存于 KB，示例仅供参考，完整内容以 KB 为准）
  │
  │  第二类（抗抑菌制剂） / 液体  → 有效成分含量, pH值, 抑菌试验, 稳定性试验（加速+长期）,
  │                     毒理学试验（皮肤刺激+眼刺激）, 重金属（铅砷汞）,
  │                     微生物指标（菌落总数+霉菌酵母+致病菌）
  │
  │  第二类（抗抑菌制剂） / 凝胶  → 同上，剂型差异不改变检测项
  │
  │  第二类（抗抑菌制剂） / 湿巾  → 基础包 + 载体材料相容性, 浸渍液含量
  │
  │  第二类（消毒剂）/液体  → 有效成分含量, pH值, 杀菌试验, 稳定性试验,
  │                     重金属（铅砷汞）, 微生物指标
  │
  │  第二类（消毒剂）/气雾  → 基础包 + 压力容器安全性, 喷雾粒径分布
  │
  │  （未分类成分）   → 基础包 + 全成分分析 + 理化性质全套
  │
  ▼
Step B — Code Node: 遍历 target_claims，逐条查「特殊宣称 → 增量检测」映射表
  │
  │  "抑菌" / "抗菌"  → +抑菌试验（如基础包未含）+ 抗菌性能评价
  │  "长效抑菌"       → 抑菌增量 + 持效性试验（多次接种）
  │  "适用于食品工业"  → +食品安全相关检测（GB 14930.2）
  │  "母婴适用"        → +皮肤刺激试验, 急性经口毒性试验
  │  "免洗"            → +残留量检测
  │  "可杀灭XX病毒"    → 触发安全层拦截（医疗暗示 R3），不生成检测方案
  │  "消毒"（不含修饰）  → +杀菌试验（如基础包未含）
  │  "清洁"            → 不增加检测项
  │
  ├── 所有宣称在表中 → 增量清单确定
  └── 表中未覆盖的宣称 → 标记为「非标准宣称」→ 进入 Step B-LLM
        │
        ▼
      Step B-LLM: LLM 评估增量项目
        约束：
        - 必须检索 KB，引用具体法规条目作为增减依据
        - 无 KB 依据时不得新增检测项
        - 输出格式：{增量项目, 法规依据, 置信度}
        - 置信度为「低」时标注「建议人工确认」
  │
  ▼
Step C — Code Node: 基础包 ∪ 增量 = 最终检测清单
  │
  └── 去重 + 按「理化 → 微生物 → 毒理 → 其他」排序
```

**设计依据**：80%+ 的消字号产品检测需求是标准组合。品类 × 剂型 × 功效宣称的排列组合有限（约 6 品类 × 6 剂型 × 10 常见宣称），表驱动即可覆盖绝大多数场景。非标准宣称才需要 LLM，且约束它必须有 KB 依据——这就不是「模型推断」而是「KB 检索+转述」。

**与三层控制的关系**：Step A/B 属于第一层（硬阻断，纯 Code Node），Step B-LLM 属于第二层（强约束，变量注入 KB 检索结果）。如果 Step B-LLM 产出了没有 KB 引用的增量，第三层校验会在输出侧拦截。

#### 3.3.2 报价预估器（S6）执行逻辑

S6 是一个纯计算节点，不进 LLM。检测机构的每个标准检测项目有精确单价。非标项目不假装能报价。

##### 价格层级模型

B2B 检测机构的报价不是引擎算一个死数字销售照念。销售有议价空间，但空间有边界。

```
┌─────────────────────────────────────────┐
│  标准价 (List Price)                     │
│  定价表查表，引擎计算                     │
│  不可被销售覆盖                           │
│  → standard_total                       │
└─────────────────┬───────────────────────┘
                  │ 客户有签约协议 → 自动替换
                  ▼
┌─────────────────────────────────────────┐
│  协议价 (Contract Price)                 │
│  客户签约时录入，引擎自动匹配               │
│  无协议 → 等同于标准价                     │
│  → contract_total                       │
└─────────────────┬───────────────────────┘
                  │ 销售在此基础上报价
                  ▼
┌─────────────────────────────────────────┐
│  销售权限价 (Sales Authority Range)       │
│  上限 = contract_total                  │
│  底价 = contract_total × 0.85            │
│  底价以上 → 销售自主决定，不触发审批        │
│  底价以下 → 需经理审批                     │
└─────────────────┬───────────────────────┘
                  │ 低于底价
                  ▼
┌─────────────────────────────────────────┐
│  特批价 (Approval Required)              │
│  引擎标记 approval_required = true       │
│  报价暂存，不输出给客户                    │
│  → 进入审批队列                           │
└─────────────────────────────────────────┘
```

`sales_discount_limit`（默认 0.85）是机构的全局参数，存在变量中，老板可调整。

##### 执行流程

```
输入: testing_items[] + urgency_level + customer_id
  │
  ▼
Step A — Code Node: 逐项查定价表
  │
  │  for each item in testing_items:
  │    price = pricing_table.get(item.code)
  │
  │  定价表示例（精确值）：
  │    有效成分含量          → ¥600
  │    抑菌试验              → ¥2,000
  │    杀菌试验              → ¥2,000
  │    稳定性试验（加速）      → ¥4,000
  │    稳定性试验（长期）      → ¥5,000
  │    毒理学—皮肤刺激        → ¥2,500
  │    毒理学—眼刺激          → ¥2,500
  │    毒理学—急性经口毒性     → ¥3,500
  │    重金属（铅砷汞）        → ¥800
  │    微生物指标             → ¥1,000
  │    pH值                  → ¥300
  │    载体材料相容性          → ¥1,500
  │    ...
  │
  ├── 全部命中 → Step B
  │
  └── item.code 不在定价表中
        │
        ▼
        停止计算。
        输出「已知项明细」+「未知项清单」。
        系统自动标记 → 强制转人工 (S8)。
        不进入 Step B。
  │
  ▼
Step B — Code Node: 价格计算
  │
  │  standard_total = sum(各项标准单价)
  │
  │  contract_total = 查协议价表(customer_id)
  │    有签约 → 使用协议价
  │    无签约 → contract_total = standard_total
  │
  │  sales_floor = contract_total × sales_discount_limit
  │
  │  urgency_factor:
  │    "普通" → 1.0
  │    "加急" → 1.3
  │
  ▼
Step C — 前端展示报价工具（给销售看，不给客户看）
  │
```

**技术实现**：v1.0 用 Coze Code Node 调用 HTML → PDF 转换（Puppeteer 或等效服务），模板为 HTML 字符串，变量替换后渲染为 PDF。v2.0 迁至 LangGraph 后，PDF 生成可作为独立微服务，支持自定义模板和批量生成。

**关键约束**：
- **R3 不进入 S6**：风险等级 R3 时状态机禁止进入报价阶段，避免给出误导性的「可以做」暗示
- **精确值，非区间**：每个检测项目有唯一的机构标准报价
- **非标转人工**：定价表中不存在的项目，停止计算，列出未知项，强制转人工。LLM 在任何情况下都不参与报价计算
- **协议价自动匹配**：客户有签约协议价时引擎自动替换标准价，销售不需要记住哪个客户什么价格
- **销售有自主空间**：`sales_discount_limit`（默认 0.85）之上的优惠销售自由裁量，之下触发审批。0.85 是全局参数，老板可调
- **税 6%**：客户报价单和 PDF 报告最终行均为「折后总计（含税）」，税款单独列一行
- **PDF 一键导出**：报价确认后系统自动装配全链路预审数据生成 PDF，客户可自行下载，链接 30 天有效
- **定价表独立管理**：v1.0 存 Coze 变量或 KB 精确表，机构销售负责人维护；v2.0 迁至 PostgreSQL，提供定价管理 API
- **折扣日志**：每次销售调价记录 `{session_id, standard_total, contract_total, final_quote, discount_%, within_authority}`，事后可审计

**与三层控制的关系**：S6 整体属于第一层（硬阻断）。不经过任何 LLM。查表失败转人工，查表成功走纯数值计算，破底价走审批流，确认后装配 PDF。校验层不参与 S6。

### 3.4 三层控制系统

引擎的可靠性不靠 Prompt 约束，靠三层控制逐级兜底。核心原则：**确定性逻辑不进 LLM**——能用 Code Node 的用 Code Node。数据采集环节也不进 LLM——用户填写固定问卷模板，Code Node 正则解析，零幻觉风险。

#### 3.4.0 核心链路：一请求三阶段

```
用户填写问卷模板
  │
  ▼
┌──────────────────────┐
│ 阶段 1：安全扫描      │  Code Node，纯字符串匹配
│ 不进 LLM             │  命中 → 拒绝模板，终止
└──────────────────────┘
  │ 未命中
  ▼
┌──────────────────────┐
│ 阶段 2：入口解析      │  Code Node，正则解析 + 归一化 + Gate
│ 不进 LLM             │  模板文本 → 结构化字段
│                      │  不全 → 返回缺失项提示
│                      │  完整 → 放行
└──────────────────────┘
  │ 放行
  ▼
┌──────────────────────┐
│ 阶段 3：合规判定      │  主模型（GLM-4.7）+ Code Node 查表
│ LLM + Code Node 协作  │  KB 检索 → 查表 → LLM 组织自然语言
└──────────────────────┘
```

**为什么数据采集不用 LLM**：Bot 侧用固定问卷模板让用户填写，Workflow 入口 Code Node 用正则解析「标签：值」格式并做归一化。整个过程是确定性的字符串处理——不需要语义理解，不会编造字段，不会漏填。相比小模型 NLU 抽取（幻觉率 ~3%，字段级准确率 ~90%），正则解析的准确率是 100%。

**为什么阶段 1 可以纯 Code Node**：安全关键词是封闭集合（「绕备案」「虚假宣传」「改报告」等），纯字符串匹配无歧义，不需要语义理解。

#### 3.4.1 第一层：硬阻断（Code Node，不经过任何 LLM）

**安全拦截**：每个请求的第一个操作永远是安全词扫描。

```
用户输入 → Code Node 关键词扫描（纯字符串匹配）
  ├── 命中规避监管/虚假宣传/篡改报告等 → 直接返回拒绝模板，终止
  └── 未命中 → 进入阶段 2（入口解析）
```

**Gate 检查**：入口解析完成后，Code Node 检查变量完整性。

```
入口解析结果 → Code Node
  检查 6 必采字段是否全部非空 + 值域合法
  ├── 不全 → Code Node 返回缺失项提示，Bot 引导用户补充
  └── 完整 → 放行至主模型 + 判定引擎
```

**风险等级判定**：不做「请根据以下规则判断风险等级」这种开放式 Prompt，而是 Code Node 查表（完整规则以 4.4 为准）。

```
function assess_risk(ingredient_status, claims, domestic_or_imported, 
                     historical_rejection, medical_keyword_hit, 
                     prior_market_flag):
    if ingredient_status == "prohibited":    → R3
    if medical_keyword_hit:                  → R3
    if historical_rejection == true:         → R3
    if prior_market_flag == true:            → R3
    if ingredient_status == "unknown":       → R2
    if domestic_or_imported == "imported":   → R2
    else:                                    → R1
```

**成分合规查表**：

```
function check_single_ingredient(raw_name, product_type):
    # Step 0: 预处理 — 剥离浓度后缀，提取 conc + unit
    name = normalize(raw_name)
    conc, unit = parse_concentration(raw_name)

    # Step 0.5: 水/溶剂基底特殊处理
    if name in ("水", "去离子水", "纯水", "纯净水", "蒸馏水"):
        return "water_base"

    # Step 1: 精确匹配 LOOKUP 索引（含标准名 + 别名 + 市场俗名）
    entry = LOOKUP.get(name)    # 命中 → allowed_active / allowed_inert
    if entry:
        restriction = check_restriction(entry.name, product_type, conc, unit)
        if restriction: → "restricted" + 限量信息
        else:           → "allowed_active" / "allowed_inert" + CAS + 法规编号

    # Step 2: 模糊子串匹配（"key in name" or "name in key"）
    for key_name, entry2 in LOOKUP:
        if key_name in name or name in key_name:
            → "allowed_active" / "allowed_inert"（标注"近似匹配"）

    # Step 3: 未命中
    return "unknown" + 标记"可能属于新消毒产品原料"
```
> GB 38850-2020 为正清单制——不在清单中 ≠ 禁用，而是 unknown（需走新原料申报）。
> 查表结果注入 Prompt，由主模型转述为自然语言。

#### 3.4.2 第二层：强约束（动态 Prompt + 变量注入）

数据采集由问卷模板 + Code Node 完成，不经过 LLM。判定阶段由主模型承担，Prompt 每轮动态拼装。

**判定 Prompt（主模型）**：

```
你当前处于：{current_state}
本阶段必须完成：{state_required_outputs}
当前已采集字段：{filled_fields_summary}
当前缺失字段：{missing_fields_list}

成分合规结果（由系统查表，非你判断）：
{ingredient_check_results}

风险等级（由系统查表，非你判断）：
risk_level = {risk_level}
触发条件：{risk_trigger_conditions}

你的任务：将以上判定结果用专业、不生硬的自然语言告知用户，按输出模板组织。

不允许做的事：{state_forbidden_actions}
如果用户试图跳过本阶段：{state_deflection_template}
```

主模型的唯一职责：将判定结果用专业、不生硬的自然语言告知用户，按输出模板组织。

#### 3.4.3 第三层：校验层（输出侧后置拦截）

前两层都失效，最后一层在输出侧拦截。

```
主模型输出 → Code Node
  │
  ├── 结构匹配：输出是否包含固定模板的所有标题？
  │   └── 不匹配 → 标记异常，触发重新生成
  │
  ├── 引用检查：合规结论是否附带知识库引用标志？
  │   └── 无引用 → 追加标注「模型生成，未经知识库验证」
  │
  └── 安全词二次扫描：输出文本是否出现幻觉信号？
      └── 命中 → 拦截，输出降级模板
```

#### 3.4.4 三层职责总览

| | 硬阻断 | 强约束 | 校验层 |
|------|------|------|------|
| 执行者 | Code Node | 主模型（判定） | Code Node |
| 触发时机 | 安全扫描：每请求最前 / Gate：入口解析完成后 | Gate 放行后 | 主模型输出后 |
| 控制方式 | 纯字符串匹配 + 变量空值判断 | 动态 Prompt + 变量注入 + 查表结果注入 | 输出侧正则 + 引用检查 |
| 适合什么 | 封闭集合匹配、确定性逻辑 | 判定结果需要自然语言转述 | 防漏 |
| 失效时 | 不存在失效（程序逻辑） | 模型不遵守时漏过 | LLM 已胡说八道 |
| 兜底方 | — | 校验层 | 用户投诉 |

**LLM 职责的再分配**：

| 角色 | 做什么 | 不做什么 |
|------|--------|---------|
| 主模型 (GLM-4.7) | 自然语言对话 + 转述判定结果 | 不自己查表判定风险等级和成分合规状态 |
| Code Node | 安全扫描、模板解析、Gate 检查、风险查表、成分查表、输出校验 | 不处理自然语言理解 |

### 3.5 KV 映射表生命周期与数据治理

引擎的判定准确性不依赖模型质量，依赖映射表的准确性。表错了，三层控制全对也是精确地输出一个精确的错误。因此需要一套「表本身的生命周期管理」机制，覆盖更新、保鲜、过渡三条线。

#### 3.5.1 映射表清单

以下四张表是引擎判定的数据底座，全部存于 KB 以 Markdown 表格形式维护，Code Node 在检索时读取：

| 表名 | 内容 | 维护方 | 变动频率 |
|------|------|--------|---------|
| `category_dosage_form_mapping` | 品类 × 剂型 → 适用法规路径 + 基础检测包 | 技术负责人 | 低（法规大版本变更时） |
| `claims_incremental_test_mapping` | 特殊功效宣称 → 增量检测项目 + 法规依据 | 技术负责人 | 中（卫健委新规/新检测标准发布时） |
| `testing_item_price_mapping` | 检测项目 → 单价区间 | 销售负责人 + 技术负责人 | 中高（市场行情波动、机构调价） |
| `ingredient_compliance_list` | 成分 INCI/CAS → allowed / prohibited / unknown + 法规编号 | 技术负责人 | 中（法规目录更新时） |

#### 3.5.2 更新机制：改表不改代码

每张表是 KB 中的一篇 Markdown 文档。更新流程：

```
机构技术负责人
  │
  ▼
在 KB 中编辑对应表格文档（修改检测项、单价、成分状态等）
  │
  ▼
保存 → KB 自动重新索引
  │
  ▼
下一次 Code Node 检索 → 读到新表 → 新规则生效
```

**配套规则**：
- 每张表必须保留至少上一个版本的备份（KB 文档版本历史），出问题时可回滚
- 任何修改在保存时自动追加一条 `changelog` 行在表末尾：`| 2026-XX-XX | 修改人 | 修改内容摘要 |`
- 涉及合规判定的表（成分清单、检测映射）修改需双人复核，报价表修改单人即可

#### 3.5.3 保鲜机制：如何发现表过时了

v1.0 不做自动化法规爬取，投入太大且误报率高。用三个低成本机制：

**机制一：KB 文档元数据 + 到期自动标记**

每张表文档头部包含元数据：

```
---
table_name: ingredient_compliance_list
last_updated: 2026-05-01
based_on_regulation: 《消毒剂原料清单》（2025版）
review_cycle_days: 90
next_review_date: 2026-07-30
---
```

Code Node 每次检索时检查 `next_review_date`：

```
读取表 → 检查 next_review_date
  ├── 未到期 → 正常使用
  └── 已到期 → 表内容正常使用，但输出追加标注：
      「本判定基于 {based_on_regulation}（{last_updated} 更新），
       法规依据已超过建议复核周期，结论仅供参考」
```

标注本身不改变引擎行为——不降级风险、不阻断流程——但让用户知情。对机构来说这是免费的法规定期 review 提醒。

**机制二：`kb_no_hit` 信号驱动人工复核**

7.2 已定义 `kb_no_hit` 埋点。在此之上加一条聚合规则：

```
Monthly Review 触发器：
  当月某个成分/检测项目出现在 kb_no_hit ≥ 3 次
  → 自动生成「待复核成分清单」
  → 推送技术负责人 review
  → 决策：新增到表中 / 确认确实不适用 / 标记待法规明确
```

高频 no-hit 不一定意味着法规变了——可能只是客户问了一个很偏的成分。但连续出现就值得看一眼。

**机制三：人工 Review 日历**

在 Coze 外部建一个最简单的流程——月度 Review check：

- 每月 1 日，检查所有表的 `next_review_date`
- 未来 30 天内到期的表，通知技术负责人 review
- Review 内容：对照最新法规原文，逐行确认表内容是否仍然准确
- Review 完成后更新 `last_updated` 和 `next_review_date`

#### 3.5.4 过渡期行为：法规已变但表尚未更新时

这是最危险的窗口——新法规生效了，但表里还是旧规则。引擎不知道这件事，照旧表判定，可能给出合规的结论给不合规的产品。

**防御策略（保守优先）**：

| 场景 | 引擎行为 |
|------|---------|
| 表在有效期内（`next_review_date` 未到） | 正常判定，不做额外标注 |
| 表已过期（`next_review_date` 已过）但 KB 仍有命中 | 使用表内容判定，输出追加「依据待确认」标注 |
| 表已过期 + 成分/项目 `kb_no_hit` | 强制标记 R2（无论其他维度如何），禁止 R1 结论。R3 不受影响（R3 是硬阻断，保守方向正确） |
| KB 文档被错误删除或损坏 | 引擎不启动判定，返回「系统配置异常，请检查知识库映射表」 |

**核心原则**：表的保鲜不确定性只影响「放行」的方向（R1→R2 过，不会 R3→R1 放）。宁可把灰色地带的咨询推给人工，不能把不合规的产品放过去。

#### 3.5.5 数据治理角色

| 角色 | 职责 | 权限 |
|------|------|------|
| **技术负责人** | 维护成分清单、检测映射表、法规依据；月度 review | 编辑成分/检测表，审批价格表变更 |
| **销售负责人** | 维护单价区间表 | 编辑价格表，提交审批 |
| **引擎系统** | 读取表、检查保鲜状态、输出标注、聚合 no-hit 信号 | 只读，不修改任何表 |

- 用户主动要求转人工 → 记录当前状态 → 转人工

### 4.2.1 状态回退与上下文级联更新机制

当前状态机在 S2→S1、S3→S1 留了回退箭头，但回退后「哪些状态结果还有效」「变量变更后下游如何联动」没有定义。真实场景中用户随时会改口——"等一下，成分不是三氯生，是苯扎氯铵"、"忘记说了，这是进口的"——如果没有回退机制，系统会带着旧上下文一路跑歪。

以下三个机制构成完整的回退体系：

#### A. 变量修改检测（Gate 检查阶段）

当前 Phase 3 只做变量非空校验。需要新增一个对比步骤：

```
Phase 3 — Code Node 执行逻辑：

Step 3a（现有）：变量完整性检查
  for each field in [6 必采字段]:
    if field.value is None or empty:
      → 追问模板，loop 回 Phase 2

Step 3b（新增）：变量冲突检测
  for each field extracted in current turn:
    if session_vars[field] exists AND session_vars[field] != new_value:
      → 标记 variable_conflict = true
      → 标记 conflict_fields[] 记录冲突字段列表
      → 不直接覆盖旧值，进入「修正确认」子流程

修正确认子流程：
  引擎输出：
    "我注意到您之前提供的信息有变化：
     - {字段中文名}：{旧值} → {新值}
     
     这个修改会影响后续的分析结果。我已为您标记，确认修改后会自动更新相关结论。
     请问还有其他需要调整的信息吗？"

  用户确认 → 执行回退（见 C 节）
  用户说"其他不变" → 执行回退，仅更新冲突字段
  用户又改了别的 → 累积冲突字段 → 一并处理
```

**设计理由**：不直接静默覆盖。用户可能只是表达不准确、输入了同义词，也可能确实要修正。静默覆盖会让用户不知道系统用了旧值还是新值；直接覆盖且自动重跑可能让用户困惑"怎么结论突然变了"。必须让用户明确感知到修改已被识别，且知道影响范围。

#### B. 变量 → 状态依赖图（级联作废规则）

每个必采字段变更后，下游哪些状态的结果会失效。这是纯粹的数据依赖，不需要 LLM 判断：

```
┌────────────────────────────────────────────────────────────────────────┐
│ 变更字段              │  级联标 stale 的状态  │  失效原因                │
├────────────────────────────────────────────────────────────────────────┤
│ product_name          │  （不触发回退）       │  仅元数据，不影响判定    │
│ dosage_form           │  S2 → S5 → S6        │  剂型影响品类分类和      │
│                       │                      │  检测基础包              │
│ main_ingredients      │  S3 → S4 → S5 → S6   │  成分是合规判定、风险    │
│                       │                      │  和检测方案的核心输入    │
│ target_claims         │  S4 → S5 → S6        │  宣称影响风险分级和      │
│                       │                      │  检测增量项              │
│ domestic_or_imported  │  S2 → S3 → S4 → S5   │  进口产品走不同法规路径  │
│                       │  → S6                │  全链路受影响            │
│ customer_type         │  S6                  │  仅影响协议价匹配        │
│ urgency_level         │  S6                  │  仅影响加急系数和周期    │
└────────────────────────────────────────────────────────────────────────┘

选采字段变更的影响：
  historical_rejection 变更 → S4 stale, S5 stale, S6 stale（退单历史直通 R3）
  usage_scenarios       变更 → 不触发回退（仅优化输出建议）
  existing_reports      变更 → 不触发回退（仅影响材料清单）
```

**回退到的状态** = 变更字段在依赖链上的最上游触发状态。例如：
- 用户改了 `main_ingredients` → 回退到 S3
- 用户改了 `dosage_form` → 回退到 S2
- 用户同时改了 `main_ingredients` 和 `domestic_or_imported` → 回退到 S2（取最上游交集）

#### C. 回退执行规则

```
触发条件：variable_conflict = true，且用户确认修改

Step 1 — 级联标 stale
  根据 B 节的依赖图，依次标记受影响的状态为 stale：
    state_results[S3] = {value: null, stale: true}
    state_results[S4] = {value: null, stale: true}
    state_results[S5] = {value: null, stale: true}
    state_results[S6] = {value: null, stale: true}

Step 2 — 保留未受影响的变量
  不在冲突字段的依赖链上的变量 → 保留已有值，不重新询问
  例：改了 main_ingredients，但 dosage_form 和 target_claims 保留

Step 3 — 自动推进
  标记完 stale 后，系统从回退的目标状态自动重跑：
    用户改 main_ingredients → 回退到 S3 → 用新成分重查合规 → 
    自动推进 S4（重算风险）→ S5（重算检测方案）→ S6（重算报价）
  
  用户不必重新输入已确认过的信息，系统主动告知：
    "已根据更新后的成分重新分析：
     - 合规状态：[新结果]
     - 风险等级：[新结果]  
     - 检测方案和报价已同步更新"

Step 4 — 安全阀
  ┌─────────────────────────────────────────────────────┐
  │ 以下情况触发自动转人工，不允许自动回退重跑：          │
  │                                                     │
  │ 1. 同一字段被修改 ≥ 3 次                             │
  │    → 用户可能在试探系统底线（换禁用成分看能不能过）    │
  │    → "检测到您多次修改成分信息，已超出自动处理范围，   │
  │       将为您转接技术专家"                             │
  │                                                     │
  │ 2. 单次修改导致风险等级从 R1/R2 变为 R3               │
  │    → 可能用户之前隐藏了敏感信息                       │
  │    → 不静默降级，必须提示用户并转人工                   │
  │                                                     │
  │ 3. 检测到同一次修正中成分从允许清单变为禁用清单        │
  │    → 直接中断，不进入 S6                             │
  └─────────────────────────────────────────────────────┘
```

### 4.4 风险分级规则

| 等级 | 触发条件（满足任一即命中） | 引擎行为 |
|------|--------------------------|---------|
| **R1 低风险** | 常规消毒成分 + 合规功效 + 成分在允许清单中 + 国产 + 无退单历史 | 正常输出检测方案 + 报价区间 |
| **R2 中风险** | 成分在允许和禁止清单之外（灰色地带）/ 功效描述边缘模糊 / 进口产品 / 植物提取物等非标准成分 / 知识库无明确依据 | 输出检测方案 + 报价区间 + 风险免责声明 + 建议人工技术审核 |
| **R3 高风险** | 成分在禁用清单 / 功效含医疗暗示（治疗/抗病毒/新冠/杀菌）/ 被其他机构退单 / 用户要求规避监管 / 先上市后补备案 | 禁止给出确定性结论 / 禁止报价 / 说明风险原因 / 强制建议转人工专家 |

**安全层规则（在任意状态实时生效）**：

| 触发信号 | 引擎行为 |
|---------|---------|
| 用户要求规避监管、绕过备案 | 拒绝 + 提示法规风险 + 引导合法路径 |
| 用户要求虚假宣传建议 | 拒绝 + 说明虚假宣传法律后果 |
| 用户要求篡改报告、虚构材料 | 直接拒绝，不做任何展开 |
| 用户输入含攻击/恶意内容 | 终止对话 + 记录 |

## 5. 异常流处理

### 5.1 业务边界场景与处理规则

以下场景是模型最容易犯错的业务盲区，必须写死处理规则。

#### 5.1.1 成分处于法规灰色地带

**场景**：产品含有植物提取物、纳米银、生物酶等成分。这些不在《消毒剂原料清单》明确允许列表中，也不在禁用清单——属于「法无明文」。不同检测机构口径不统一。

**处理规则**：
1. 知识库命中「允许清单」→ 输出 R1，引用依据
2. 知识库命中「禁用清单」→ 输出 R3，引用依据
3. 两个清单都没命中 → **禁止推断**，标记 R2，输出「该成分在现行消字号法规目录中暂无明确收录，建议提交省级卫健委进行法规释义确认」

#### 5.1.2 功效宣传暗示医疗用途

**场景**：用户描述中出现「治疗湿疹」「抑制幽门螺杆菌」「抗病毒」「杀灭新冠病毒」等。消字号产品禁止此类宣传，但用户可能无意中用词。

**处理规则**：
1. 检测到医疗暗示关键词 → **立即中断当前分析**
2. 输出：「需要提示：消字号产品的功效宣传不能涉及疾病治疗、抗菌、抗病毒等医疗用途表述。您提到的『XXX』可能触及这个边界。请问您是否需要我基于消字号合规范围继续分析？」
3. 用户确认继续后才恢复流程

#### 5.1.3 进口产品合规路径分叉

**场景**：进口产品不需要《消毒产品生产企业卫生许可证》，但需要进口备案材料和原产国自由销售证明。按国产流程输出会导致材料清单和周期估算全错。

**处理规则**：
1. S1 采集时 `domestic_or_imported` 为必采字段
2. 该字段为空时，所有后续结论标注「基于国产产品假设，如为进口产品请纠正」
3. 字段为 `imported` → 状态机切换进口分支：跳过卫生许可证步骤，增加原产国文件清单

#### 5.1.4 客户隐瞒退单历史

**场景**：客户在其他机构被退过单，来时不主动说——怕直接说了会被拒绝或报高价。

**处理规则**：
1. S1 阶段主动询问：「您的产品之前是否在消字号备案或检测过程中被退回或拒绝过？」
2. 客户回避 → 追问一轮：「了解备案历史是为了帮您规避之前的问题，提高本次通过率」
3. 两轮后仍回避 → 不再追问，输出结论时标注「未获取退单历史，以下分析基于首次申报假设」
4. 确认有退单历史 → 进入退单诊断子流程，额外采集退单原因，R2 以上走人工

#### 5.1.5 套装/组合/系列产品

**场景**：用户提供的是包含多个 SKU 的套装。不同品类备案路径不同，不能当作一个产品分析。

**处理规则**：
1. 检测到「套装」「系列」「一套」「组合」「搭配使用」或同时出现多个剂型 → 触发拆分追问
2. 追问：「消字号备案以单个产品为单位。请问这些产品的成分和功效是否相同？如果不同，需要逐个分析」
3. 相同 → 合并处理；不同 → 逐个采集，每个产品只先采 3 个核心字段（品名/剂型/核心成分）做快速评级

#### 5.1.6 先上市后补备案

**场景**：产品已在销售，因举报/抽检/平台要求下架才来咨询。已在市场上流通的产品有公开记录，违规风险更大。

**处理规则**：
1. 检测到「已经在卖」「上市了」「被查了」「被举报」「平台下架」→ 标记 `urgency_level: high`，跳过常规流程直接进 S4
2. 输出时增加：「由于产品已在市场流通，建议尽快核查现有标签是否符合《消毒产品标签说明书管理规范》。如不合规，先行整改再提交备案」
3. 强制建议人工介入

#### 5.1.7 成分信息可能不完整

**场景**：客户可能仅提供主料而隐瞒了敏感成分，或用了过于笼统的描述。

**处理规则**：
1. 检测到模糊表述（「植物提取物」「活性成分」「专利配方」「复合成分」「表面活性剂」等）→ 追问：「『XXX』是笼统的类别名称。备案需要具体成分的 INCI 名称或 CAS 号，能否提供完整成分列表？」
2. 两轮追问后仍不提供 → 标记「成分信息不完整」，**不输出合规结论**
3. 不判断客户动机，只看信息完整性

### 5.2 技术降级策略

| 依赖 | 故障场景 | 降级方案 |
|------|---------|---------|
| 知识库 (VikingDB) | 检索超时或不可用 | 告知「检索服务暂时不可用」，基于已有信息给出初步框架，标注「未经知识库验证」 |
| Coze Workflow | 工作流执行失败 | 回退到 Prompt 驱动的纯文本分析，标注「本结论由模型生成，未经规则引擎验证」 |
| 模型 API | 调用超时或限流 | 返回「当前咨询量大，请稍后再试」，记录未完成的会话状态 |

## 8. 降 Token 策略与风险置换

每项降本措施都是用某个维度的风险换 Token，不能只看省多少。

| 降本策略 | 预估节省 | 置换出去的风险 | 底线 |
|---------|---------|---------------|------|
| FAQ 静态缓存（不调模型） | 20-30% | 边界 case 误匹配——错误的信息比没信息更糟 | 仅限「备案流程步骤」等纯信息查询。成分/法规判定**不走缓存** |
| S5 之后摘要压缩历史上下文 | 30-50% | S5 之前压缩会丢关键字段，导致检测方案错误。S5 之后丢信息影响较小（报价不准） | 仅在 S5 生成后触发。压缩后必须重新回显已采集核心字段 |
| 简单任务规则匹配不调模型 | 10-15% | 规则覆盖不全，用户换个说法就匹配失败 | 仅用于 S0 引导语和 S1 追问话术 |
| 缩短状态机 Prompt | 15-25% | 状态约束减弱 → 跳步率上升 → 信息不全就输出结论 | **不做。** 状态机是骨架 |
| 缩上下文轮数 | 40-50% | 多轮对话上下文断裂，状态机失效 | **不做** |
| 减少 KB 检索次数 | <5% | 鼓励模型凭记忆编造 | **不做** |

**建议方案**：FAQ 缓存 + S5 后摘要压缩，两项合起来节省 30-50%，代价可控。数据采集已改用问卷模板 + Code Node，该环节零 Token 消耗。

### 10.4 风险判定准确率（人工对比）

这是测试金字塔顶端唯一需要人工参与的环节。

```
方法：
  1. 抽取 50 条真实预审对话（来源：阶段 3 完成后的生产日志）
  2. 引擎对每条输出 risk_level + trigger_conditions
  3. 机构技术负责人独立判定（看不到引擎的结果）
  4. 对比 → 计算一致率
  5. 不一致的 case 逐条归因

指标与目标：
  ┌─────────────────┬──────────┬──────────────────────┐
  │ 指标             │ 目标     │ 不达标时               │
  ├─────────────────┼──────────┼──────────────────────┤
  │ 整体一致率       │ ≥ 90%    │ 检查分歧 case 归因     │
  │ R3 召回率        │ ≥ 95%    │ 宁可错拦，不可漏拦      │
  │ R1 精确率        │ ≥ 90%    │ 放行的确实没问题        │
  └─────────────────┴──────────┴──────────────────────┘

分歧归因分类：
  引擎规则需补充 → 更新 KB 映射表
  人工判错       → 训练材料（不修改引擎）
  KB 数据过期    → 触发表保鲜流程（见 3.5.4）
  法规本身不明确  → 标记为 known_ambiguous，不做修改
```

### 10.5 回归测试

每次修改 KB 映射表后自动触发，确保改表不破坏已有正确行为。

```
触发条件：任何 KB 映射表文档被修改保存
延迟：文档保存后 5 分钟内自动启动

回归测试范围（按修改的表自动选择）：
  改了成分清单     → 跑全部 Code Node 单元测试 + 成分相关 E2E
  改了定价表       → 跑全部报价单元测试 + 报价 E2E + PDF 生成
  改了检测映射表   → 跑全部检测方案单元测试 + 检测 E2E

回归测试集：≥ 30 条历史通过的测试用例

门槛：
  - 所有历史通过的用例必须继续通过
  - 如有失败 → 分类处理：
    ├── 预期内（法规确实变了，旧断言不再适用）→ 更新测试用例 + 记录
    └── 意外破坏（改 A 表导致 B 功能坏了）  → 阻断上线 + 修复
```
