## 三、致命漏洞详情（3 项 P0 — 全部未落地 ❌）

### P0-1：S2 品类判定的输入字段不在 6 个必采字段中

- **位置**：3.3 核心模块表 vs 4.3 必采字段 Schema
- **问题**：3.3 定义 S2「产品分类器」输入为"产品类型描述 + 剂型 + 用途"，但 4.3 的 6 必采字段中**没有 `product_type` 字段**。S2 此时品类未知，它用什么做输入？
- **根因**：设计阶段未走通完整数据流——每个判定模块的输入必须能溯源到已采集的变量，但这份溯源未做。
- **后果**：开发写 S2 Code Node 时发现输入参数对不上，要么临时加字段打乱采集流程，要么硬编码假设导致分类错误。
- **建议修复**：将 S2 输入改为 `target_claims + dosage_form + main_ingredients`，删除不存在的"产品类型描述"。增加一张"输入溯源表"（见审计报告 Before/After 示例）。

### P0-2：报价引擎的增值税计算存在双重计税风险

- **位置**：3.3.2 Step C 报价工具
- **问题**：定价表中 ¥600、¥2,000 等单价**未声明是含税价还是未税价**。在 B2B 检测机构实务中，公示标准报价几乎都是含税价。如果 ¥600 已经是含税价，Step C 再 `+6%` 就是重复计税。
- **后果**：给客户报出比实际成本高 6% 的价格（如 ¥15,900 vs 实际 ¥15,000），在竞对林立的检测市场直接丢单。或者反向——报低了 6%，机构亏本。
- **建议修复**：在定价表或 4.3 中新增全局配置变量 `tax_inclusive_pricing`（boolean）和 `tax_rate`（0.06），Code Node 据此决定是否需要加税。

### P0-3：Markdown 表格作为判定数据底座的可靠性问题

- **位置**：3.5 映射表清单 + 3.5.2 更新机制
- **问题链**：
  1. VikingDB 是**向量数据库**，不是结构化存储。语义检索返回的是"最相关的文档片段"，不是"精确的表行匹配"
  2. Code Node 需要解析检索返回的 Markdown 表格，Markdown 解析对格式极其敏感（多一个空格就变了）
  3. 成分合规检查 `check_ingredient` 的核心逻辑 `if kb_hit_result == "in_allowed_list"`——这个 `kb_hit_result` 来自 VikingDB 语义检索，可能返回相邻成分的行而非精确匹配
- **后果**：一个成分的合规判定可能因为 KB 检索返回了相邻行而得出相反结论。三层控制全对，精确地输出一个精确的错误。
- **建议修复**：成分合规清单和定价表从"KB Markdown 表格"迁移为**结构化 JSON/CSV 文件**存储于 Coze 变量或外部数据源，Code Node 直接读取做 exact_match，不经过向量检索。只有法规解读类查询才走 VikingDB 语义检索。此修复与 `v1.0-diagnostic-patch_rag-retrieval.md` 的结论（结构化数据走精确匹配，不走向量检索）方向完全一致。

## 四、重要建议详情（3 项 P1 — 全部未落地 ❌）

### P1-1：定价表单价的含税/未税属性未定义

- **位置**：3.3.2 Step A 定价表示例
- **问题**：与 P0-2 相关联但独立——即使修正了计算逻辑，定价表本身仍然没有标注单价是否含税。这导致后期维护定价表时，录入者不知道填含税价还是未税价。
- **建议**：定价表增加一列 `price_tax_status: "inclusive" | "exclusive"`，或在表头明确标注基准。

### P1-2：S5 B-LLM 的"置信度"由 LLM 自己判定

- **位置**：3.3.1 Step B-LLM
- **问题**：要求 LLM 输出 `{增量项目, 法规依据, 置信度}`，但置信度是 LLM 自己判定的——让考生给自己的考卷打分。幻觉时 LLM 通常是高度自信的。
- **建议**：置信度不由 LLM 自己判定，改为 Code Node 根据客观信号判定：引用 KB 文档是否在有效期内、KB 检索 hit_count ≥ 2、增量项目在映射表中是否有相似项。

### P1-3：小模型不可用时缺少降级路径

- **位置**：3.4.0 核心链路 + 5.2 技术降级表
- **问题**：5.2 降级表只有"模型 API 超时 → 请稍后再试"，但小模型（GLM-4-flash）和主模型（GLM-4.7）挂了应该是不同的降级策略。小模型挂了能否降级到主模型做 NLU（代价高但能继续服务）？
- **建议**：5.2 新增一条：小模型不可用 → 降级到主模型做 NLU 抽取，Prompt 切换为抽取模式（仅输出 JSON），标注"当前服务降级运行"。

## 五、优化建议详情（5 项 P2 — 全部未落地 ❌）

### P2-1：`sales_discount_limit = 0.85` 硬编码风险

- **位置**：3.3.2 价格层级模型
- **问题**：PRD 说 0.85 是"全局参数，老板可调整"，但如果硬编码在 Code Node 中，每次调整都要改代码。
- **建议**：在 4.3 中新增一个系统配置变量组 `global_config`，包含 `sales_discount_limit`、`tax_rate`、`quote_validity_days` 等所有可调参数。

### P2-2：测试用例 ID-RISK-05 逻辑不可能

- **位置**：10.2.3 风险判定查表测试用例
- **问题**：ID-RISK-05 测试"用户触发规避监管（安全层已拦截）→ R3"，但规避监管关键词在 Phase 1（安全扫描）就被拦截了，请求根本不会到达 `assess_risk()` 函数。**测试的是一个不会被执行到的代码路径。**
- **建议**：删除 ID-RISK-05，或改为验证 Phase 1 安全扫描对该输入的拦截行为（归类到 ID-SEC 系列）。

### P2-3：安全阀"同一字段修改 ≥3 次 → 转人工"存在误杀

- **位置**：4.2.1 安全阀规则 1
- **问题**：用户补充成分信息（"还有甘油"）和替换成分（"不是三氯生，是苯扎氯铵"）都会累计计数器。补充不应触发试探检测。
- **建议**：将计数器限定为"值替换型修改"（`old_value != null AND new_value != old_value AND new_value NOT superset of old_value`）。

### P2-4：NLU 抽取正确但事实错误——Gate 无法拦截

- **位置**：3.4.0 Phase 3 + 4.2.1
- **问题**：Gate 只做变量非空校验。如果小模型把 `dosage_form` 正确抽取为"液体"但实际是"凝胶"——Gate 看到字段非空就放行了。**正确抽取了错误信息，Gate 无法拦截。**
- **建议**：在 S2 品类判定完成后，增加一个确认步骤：将判定出的品类回显给用户确认。

### P2-5：Changelog 未更新（自 2026-05-20 后）

- **位置**：第 11-28 行
- **问题**：Changelog 止于 2026-05-20，此后用户可能有微调但未记录。本次审计发现的任何实际修改也需记录。
- **影响**：低（不影响方案），但后续无法追踪演进历史。

## 六、下一步需思考的盲点（8 个维度）

### 6.1 判定模块的数据流溯源

- **问题**：S2-S6 每个模块的输入参数必须能溯源到具体的已采集变量。当前 PRD 在 3.3 表格中定义了输入输出，但输入字段名和 4.3 变量名之间存在不一致。
- **需要回答**：每个判定模块的每个输入参数的**确切变量名**是什么？能否画一张完整的"变量 → 判定模块 → 输出变量"的数据流图？
- **相关内容**：审计报告 Before/After 示例中的"输入溯源表"可作为起点。

### 6.2 Coze VikingDB vs 结构化存储的分工边界

- **背景**：P0-3 指出 Markdown 表格做判定底座不可靠。`v1.0-diagnostic-patch_rag-retrieval.md` 已论证了"结构化数据走精确匹配、法规解读走语义检索"的方向。
- **需要回答**：
  - 哪些数据必须走结构化存储（Coze 变量 / 外部 JSON）？
  - 哪些数据可以继续走 VikingDB 向量检索？
  - 两者的分界规则是什么？
  - 如果 Code Node 不能直接读取外部数据源，Plan B 是什么？
- **关联**：v2.0 PRD（消字号售前咨询v2.0-prd.md）的 8.7 节已定义了成分数据表 Schema，但未说清楚数据表在 Coze 运行时的"读"路径。

### 6.3 Code Node 在 Coze 平台的真实能力边界

- **需要回答**：
  - Code Node 支持的代码量上限（行数/字符数）？
  - 是否支持 import 外部库（如 Python 的 `json`、`re`、`math`）？
  - 能否发起 HTTP 请求调用外部 API？
  - 能否读取 Coze 知识库检索的原始结果（而非 LLM 处理后的摘要）？
  - 执行超时限制是多少？
- **为什么关键**：PRD 中大量判定逻辑被设计为 Code Node 查表。如果 Code Node 能力不足以执行这些逻辑（如无法处理 200 行的成分清单 JSON），整个架构就需要重新设计。

### 6.4 NLU 小模型的消字号领域术语识别率

- **问题**：当前假设 GLM-4-flash 能做成分名、剂型、功效宣称的实体抽取。但通用 NLU 模型对"苯扎氯铵""聚六亚甲基胍盐酸盐""卡波姆"等专业术语的识别率可能极低。
- **需要回答**：能否用 20 条真实客户场景输入（含专业术语）先做抽取 accuracy benchmark？如果关键字段（`main_ingredients`）的抽取准确率 < 90%，是否需要 few-shot prompt 优化或换模型？
- **关联**：PRD 10.3 已定义 NLU 测试集框架（50 条），但未构建具体用例。v2.0 PRD 检查点 4.1 也标注了同样的盲点。

### 6.5 管线 C（输出校验）的误拦截风险

- **问题**：审计报告 P0-3 和 `v1.0-diagnostic-patch_rag-retrieval.md` 的 4.3 节都提到了输出校验层。但补丁文件也坦承：正则提取法规引用的漏判/误判率未知，校验失败后的处理策略（静默拦截？显式警告？）未定。
- **需要回答**：
  - 校验层拦截后是静默删除 + 重生成，还是显式标注"此条未经知识库验证"？
  - 如果一条输出中 3 条正确 + 1 条无法验证，是拦截整条输出还是仅标注那 1 条？
  - 校验层本身的可靠性如何验证？
