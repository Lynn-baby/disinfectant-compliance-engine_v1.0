## 四、下一步需要思考的盲点（6 个维度）

### 4.1 管线 A（NLU）的模型选型
- 当前假设用 GLM-4-flash 做实体抽取，但未验证其消字号领域术语的抽取准确率。
- **盲点**：通用 NLU 模型对"苯扎氯铵""聚六亚甲基胍"等专业成分名的识别率可能远低于通用实体。需要先用 20 条真实用户输入做抽取 accuracy benchmark，再决定是否需要对 flash 模型做 few-shot prompt 优化或换模型。

### 4.2 管线 B（确定性引擎）的 Code Node 实现边界
- 当前在 Coze 平台上，Code Node 能否执行 8.7 中定义的查表伪代码（exact_match、fuzzy_match、区间计算）？
- **盲点**：Coze Code Node 的 JS/Python 运行环境、可用内存、外部数据源接入方式（数据表存哪里？Code Node 怎么读？）。如果 Coze Code Node 不能直接读外部数据表，管线 B 的"确定性引擎"就落不了地。

### 4.3 管线 C（输出校验）的执行成本
- 管线 C 定义了 5 步校验（C1-C5），每轮对话都跑一遍意味着每轮多 1 次 LLM 调用。
- **盲点**：延迟和成本是否可接受？是否应该按风险分级做差异化校验（R1 只跑 C3+C5，R3 全跑）？当前方案未定义校验深度与风险等级的对应关系。

### 4.4 状态回退的测试覆盖
- 3.1.1 定义了 6 种回退场景，但验收测试用例（7-最小闭环定义）中没有任何一条专门测试回退。
- **盲点**：回退是最容易出 Bug 的状态机逻辑——回退时变量是部分清空还是全部保留？回退后 SPIN 策略是否跟着回退？需要至少 2 条专门的回退验收用例。

### 4.5 并发用户场景
- 当前全部设计假设单用户单会话。如果同时有 10 个客户咨询，Coze 的会话隔离、变量隔离、KB 检索并发是否撑得住？
- **盲点**：Coze 的并发限制和排队策略。如果有限，需要在产品设计中加入"等待提示"或"预约回访"机制。

### 4.6 数据闭环与模型迭代
- 当前埋点（6.2）覆盖了销售漏斗，但没有覆盖合规判定准确率的追踪。
- **盲点**：怎么知道管线 B 的判定是对是错？需要定义"合规判定 ground truth"的采集机制——是人工抽查？还是等客户实际备案结果回传？没有 ground truth，风险分级模型永远无法优化。
