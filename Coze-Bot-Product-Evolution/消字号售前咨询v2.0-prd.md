## 1. 背景与目标

### 1.1 业务背景

当前已上线「消毒合规顾问」Bot（v1.0），基于 Coze + 火山知识库（VikingDB），定位是帮助消毒产品厂商解决检测、消字号备案和合规问题。核心数据：

- 知识库文档 4 篇，总计 ~6,500 字，尚未被检索使用（hit_count: 0）
- Bot 使用次数 0，尚未进入真实用户验证阶段
- 模型配置：GLM-4.7，temperature 0.1，上下文仅 3 轮
- 无工作流、无变量、无结构化字段采集

v1.0 本质是一个**无状态 RAG Bot**——"用户提问 → 知识库检索 → 模型回答"。缺少企业级 Agent 所需的状态机、风险控制、结构化采集等关键模块。

### 1.2 产品定位

> **面向终端客户的 AI 销售顾问**，非检测机构内部工具。Agent 的人设是「国内中大型第三方检测机构的资深销售顾问」，拥有 10 年行业经验，擅长 SPIN 销售法和销售漏斗模型。终端用户通过 Agent 直接获取合规评估和报价——Agent 既是技术顾问，也是销售。

**与旧版的核心差异**：旧版（v1.0 合规预审引擎）是内部工具，销售用。新版（v2.0 AI 销售顾问）直接面对终端客户，Agent 自己就是销售。

### 1.3 产品目标

1. **建立专业信任** — 用合规知识树立权威，让客户觉得"这个人/Agent 懂行"
2. **驱动转化** — 不是给客户一份报告就结束，而是推动客户从"问问看"走到"留资/成交"
3. **精准报价** — 合规判定正确的前提下，报价要带价值包装和 CTA，不做单纯查表
4. **沉淀数据** — 每条对话记录转化为结构化客户数据，驱动线索评分模型持续优化
5. **赋能中小中介** — 让没有内部实验室的中介也能 2 分钟内给自己客户出方案

### 1.4 成功指标

| 指标 | 当前值 | 目标值 (v2.0) | 衡量方式 |
|------|--------|---------------|----------|

## 2. 用户分析

### 2.1 Agent 人设

> Agent 是**国内中大型第三方检测机构的资深销售顾问**，拥有 10 年消字号合规行业经验。同时掌握了 SPIN 销售法和销售漏斗模型。面对终端客户时，Agent 的身份不是客服——是专家销售。说话像在给客户做咨询，不是念法规条文。

Agent 的能力边界：
- **合规层**：品类判定、成分查表、风险分级、检测方案生成、报价计算——这些是硬功夫，通过 Code Node + KB 保证正确性
- **销售层**：SPIN 对话引导、需求挖掘、价值包装、CTA 推动——这层靠 Agent Prompt 发挥，但受合规层约束（R3 禁止推销）

### 2.2 目标用户画像

| 角色 | 典型场景 | 核心痛点 | SPIN 切入策略 |
|------|---------|---------|-------------|
| **代工厂/工厂质量负责人** | 客户来单需要判断能不能接，接了什么检测，多少天出报告 | 判断慢丢单、判断错赔钱。技术人员经验不可复制，人走能力走 | **P** - "如果接了一个成分不合规的产品，不光检测费赔进去，退单记录多了卫健委会重点监管你们" |
| **品牌方产品经理** | 拿到新配方，想确认能不能做消字号备案、花多少钱、多久上市 | 多家比价信息不透明，看不懂方案差异。最怕低价方案漏检项导致备案被打回 | **I** - "少报一项检测省 2000 块，但备案被退回补测多花 2 万还耽误 2 个月，竞品抢先上市了" |
| **检测行业中小服务机构（中介）** | 手上多个客户同时问，需要快速出方案报给客户，自己没有实验室靠转包 | 大机构销售回复慢，中介的客户就跑了。转包漏项自己赔钱 | **N** - "我们给中介客户提供专属报价通道，2 分钟出方案，你直接转给自己的客户，中间利润空间你自己把控" |

### 2.3 用户痛点（SPIN 结构化）

每个用户角色的痛点用 SPIN 四层拆解，直接对应 Agent 对话策略：

**代工厂质量负责人**：
- **S 现状**：技术员人工判断成分合规和检测清单，翻资料、问熟人、凭经验。新人不敢独立判断。
- **P 难点**：判断慢→客户流失。判断错→接了不合规的单→备案被退→退单记录→卫健委重点监管→后续所有备案更难通过。
- **I 影响**：退一次单直接损失检测费+时间，间接损失客户关系+机构信誉+监管评级。新人培养 6-12 个月，刚上手可能跳槽。
- **N 方案**：24 小时在线的 10 年经验合规顾问，2 分钟出结论+报价。不离职、不看心情、每次输出标准一致。

**品牌方产品经理**：
- **S 现状**：找多家检测机构比价，每家给方案不完全一样。靠人脉打听，信息不透明。
- **P 难点**：看不懂方案差异——A 机构 7 项报价 2w，B 机构 5 项报价 1.5w。可能 B 少报了检测项，备案时被打回。
- **I 影响**：补测更贵，上市窗口期丢失 2-3 个月，竞品抢先铺货。若因不合规被处罚，品牌信誉受损、经销商退货。
- **N 方案**：一个能逐项解释"每项检测为什么必须做、不做有什么风险"的专家，帮你做明智决策。

**中小检测中介**：
- **S 现状**：作为中介帮客户找检测机构，自己没实验室，赚转包差价。每次都要问大机构销售，回复慢。
- **P 难点**：大机构销售回复慢→中介的客户就跑了。响应速度是中介唯一护城河。转包时漏检测项→后面扯皮自己垫钱。
- **I 影响**：丢一个客户不只是丢一笔——中介行业靠口碑吃饭，一个客户不满意可能丢掉一整个代工厂的供应商名额。
- **N 方案**：专属报价通道，2 分钟出方案，中介直接转给自己客户，中间利润自己把控。

### 2.4 核心用户场景

**场景 A：代工厂接单判断**
> 代工厂质量负责人老赵收到客户发来的洗手液配方，需要判断能不能接。他打开 Agent，粘贴成分。Agent 边采集信息边追问："这个产品主要在什么渠道卖？线上还是线下？" 采集完成后自动判定为抗抑菌剂，成分全在允许清单，R1 低风险。Agent 输出 7 项检测清单和报价，同时说："这个配方没风险，可以放心接。现在锁定排期的话，7 天内就能启动检测。留个手机号，我让技术主管直接和你对接样品寄送。" 老赵留了电话，10 分钟后收到人工确认。拿下订单。

**场景 B：品牌方比价决策**
> 品牌方产品经理小张手里有竞对 A 机构的 5 项 1.5w 方案，来找 Agent 对比。Agent 逐项分析差异："他们少报了稳定性试验和抑菌试验。这两项不是可选——消字号备案强制要求。如果按他们的方案提交，备案会被退回，补测反而多花 4 万。我们的方案是标准全套，一次性通过。" 小张明白了差异，选择本机构方案。

**场景 C：中介批量咨询**
> 中小中介老板阿芳手上同时有 3 个客户问不同产品。她打开 Agent，快速录入三个产品的核心信息（品名+剂型+成分）。Agent 对每个产品给出风险等级和检测方案。其中 1 个触发 R3（含禁用成分），Agent 说："这个含三氯生，消字号明确禁用。建议你直接回复客户无法备案，保住你的专业形象。" 另外 2 个正常报价，阿芳直接转发给客户，2 分钟搞定。

**场景 D：退单诊断**
> 代工厂客户之前在某机构备案被退回，来找 Agent 分析原因。Agent 进入退单诊断子流程：采集退单原因→分析是否为合规问题→重新判定风险→给出补救路径。如是检测漏项导致，Agent 主动说明："这个问题我们不会发生，我们的检测方案是有查表兜底的。"

**场景 E：比价防御**
> 客户说"别家报价比你们便宜 30%"。Agent 不降价，触发 SPIN-I："我帮您看看他们报的方案。消字号备案基础检测项是固定的——少了抑菌试验或者稳定性试验，报价当然便宜。但备案时这些缺失项会被卫健委打回，补测费比正常测贵 50%，而且周期从头算。您更在意这次少花几千，还是确保一次性通过？"

## 3. 业务闭环

### 3.1 整体流程

```
用户进入
  │
  ▼
S0 初始接待 ──→ 了解用户意图，介绍自身能力边界
  │
  ▼
S1 基础信息采集 ──→ 按 Schema 逐项采集必填字段
  │                  缺失关键字段 → 禁止进入结论阶段
  ▼
S2 产品类别判定 ──→ 抗抑菌剂 / 普通消毒剂 / 无法判定
  │
  ▼
S3 成分合规分析 ──→ 检索知识库 + 法规数据库
  │                  高风险成分 → 优先触发风险提示
  ▼
S4 风险等级评估 ──→ R1 低 / R2 中 / R3 高
  │                 R3 → 禁止输出确定性结论
  ▼
S5 检测方案生成 ──→ 根据品类 + 功效宣传输出检测清单
  │
  ▼
S6 报价与周期预估 ──→ 区间报价 + 参考周期
  │                    前置条件：必采字段完整 + 非 R3
  ▼
S7 咨询摘要生成 ──→ 结构化摘要 + 线索评分
  │
  ▼
S8 转人工（条件触发）──→ R3 高风险 / 用户主动要求
```

### 3.1.1 状态回退机制（State Regression）

状态机不是单向不可逆的。用户在任意阶段新增、修正、或补充信息时，系统必须支持状态回退和重算。

#### 3.1.1.1 回退触发条件

| 触发场景 | 触发条件 | 回退目标状态 | 说明 |
|---------|---------|------------|------|
| 新增/修正成分 | 用户在 S3 之后的任意阶段提供新的成分信息或修正已采集的成分 | **S3** | 成分合规分析必须基于完整成分列表重跑 |
| 修正产品类型 | 用户在 S2 之后修正 `product_type`（抗抑菌剂↔普通消毒剂） | **S2** | 不同品类对应不同法规路径和检测清单 |
| 修正产地 | 用户在 S3 之后将 `domestic_or_imported` 从国产改为进口（或反之） | **S2** | 国产/进口分支的合规路径不同 |
| 修正功效宣传 | 用户在 S4 之后新增/修正功效声称（如补充了医疗暗示词） | **S4** | 重跑风险评级 + 安全扫描 |
| 补充退单历史 | 用户在 S5 之后首次透露之前有备案被退的历史 | **S1（退单诊断分支）** | 退单历史改变整体判定路径 |
| 用户主动纠错 | 用户说"等等，我之前说的XX不对"或类似纠错表述 | 该字段首次采集的状态 | NLU 识别纠错意图，回退到该字段所属状态 |

#### 3.1.1.2 回退执行规则

```
state_regression(trigger_event):
  1. 识别触发场景，确定回退目标状态 target_state
  2. 标记从 target_state 到当前状态之间所有状态的产出为「待重算」
  3. 保留 target_state 之前的所有已采集字段（不回退已完成的信息采集）
  4. 更新触发字段的值（新增/修正/补充）
  5. 从 target_state 重新推进状态机
  6. 主动告知用户回退发生
```

#### 3.1.1.3 回退通知模板

回退发生时，Agent 必须主动告知用户，不得静默重算：

> "您刚提供的 [字段名] 信息可能影响之前的分析结论。我重新帮您梳理一下——"

通知要素：
- 说明回退原因（哪个信息变了）
- 说明影响范围（哪些之前的结论需要重看）
- 不道歉（"不好意思"之类的客服腔），体现专业——"我们重新过一遍"而非"对不起我之前搞错了"

#### 3.1.1.4 回退边界约束

- **不回退已完成的硬阻断检查**：安全扫描（B1）结果不回退——已拦截的内容不会因为用户补充信息而放行
- **不回退已推送的外部事件**：如果已经在 S6 推送了留资/CRM，回退不撤回已推送的事件（CRM 侧可能已创建线索）
- **回退次数不限**：用户可能在一次会话中多次修正信息，每次都正确回退
- **回退不改变会话 ID**：同一个 `session_id` 内完成，埋点 `state_transition` 记录 `regression` 类型的 transition

#### 3.1.1.5 回退与 SPIN 策略的关系

状态回退时，SPIN 对话策略也随状态回退：
- 回退到 S2 → SPIN 策略回到 S（了解背景）/ P（揭示差异），不回退到已完成的 N（需求满足）
- 如果回退前已经推过强 CTA，回退后**不重推同一个 CTA**（避免"你刚才已经留过电话了，但..."的尴尬）
- 回退后的 SPIN 话术应衔接回退通知："重新看了一下，根据你刚提到的 XX 成分..." 而非从头开始尬聊

### 3.3 关键转化节点

| 节点 | 当前状态 | v2.0 目标 |
|------|---------|----------|

### 3.4 核心架构：双层叠加模型

Agent 的可靠性不靠 Prompt 约束保证，靠两层架构各司其职。这个模型是整个系统的核心设计决策——它解决了"合规判定必须零错误"和"销售对话必须有人情味"两者的共存问题。

#### 3.4.1 为什么需要双层？

单层模型会出两种问题：

- **只用状态机**：像一个填表机器人。信息采完了→出结论→出报价。对话生硬，没有销售力。客户看完"哦"一声就关了。
- **只用 SPIN Prompt**：像一个纯销售。为了成交可能淡化合规风险，R2 说成"问题不大"，R3 说成"可以先测着看看"。幻觉高，会出事故。

两层叠加，各管各的：

```
┌─────────────────────────────────────────────────────┐
│              销售层：SPIN + 销售漏斗                  │
│  控制对话策略、需求挖掘、价值包装、CTA 推动           │

```

#### 3.4.2 合规层（技术底座）— 三条管线规格

合规层由三条管线串行组成。每条管线有明确的输入/输出 Schema 和失败处理。管线 A 和管线 C 可调用 LLM（NLU 抽取和转述），管线 B **全部为 Code Node 确定性逻辑，不进 LLM**。

**管线间数据流**：

```
管线 A (NLU+归一化)
  → Normalized_Input_JSON
    → 管线 B (确定性判定)
      → Compliance_Output_JSON
        → 管线 C (输出校验) + 销售层 Prompt 拼装
```

**Token 预算（管线 A 和管线 C 涉及 LLM 调用）**：
- 管线 A (NLU 抽取): ~200 token/prompt + ~150 token/output，每次用户输入触发 1 次
- 管线 B (Code Node): 0 LLM token
- 管线 C (输出校验 LLM): ~300 token/prompt，每次 Agent 回复前触发 1 次
- 管线 A+C 合计约占 Coze 月度 Token 预算的 25-35%（其余为对话主模型）

**管线 B 的执行顺序保证**：
B1→B2→B3→B4→B5→B6 严格串行。任一步骤中断（B1 拦截 / B2 缺失字段 / B3 查表异常），不执行后续步骤。中断时已执行步骤的输出保留，用于告知用户当前状态和中断原因。

销售层拿到了管线 B 输出的 `risk_level = R3`，可以调整说话方式（"为了保护您的权益，我们建议..."），但不能改变结论（"可以测"）。**合规层产出的判定结果是不可被销售层扭曲的事实。**

#### 3.4.3 销售层（转化引擎）

新增，当前 PRD 完全缺失。Agent 在每个状态机阶段叠加对应的 SPIN 对话策略和漏斗推动动作：

| 状态机阶段 | 合规层产出 | SPIN 对话策略 | 漏斗阶段 | CTA 动作 |
|-----------|----------|-------------|---------|---------|
| S0 初始接待 | 安全扫描结果 | **S - 了解角色**："看您的描述，您应该是品牌方的产品经理？" | Awareness | 引导进入咨询 |
| S1 信息采集 | 必采字段填充状态 | **S - 挖背景**："这个产品主要在什么渠道卖？线上还是线下？" 边采边挖，不是填表式追问 | Interest | 无（信息不完整不推） |
| S2 品类判定 | 品类标签 + 法规路径 | **P - 揭示差异**："抗抑菌剂和普通消毒剂的备案要求不一样，很多人搞混了" | Interest | 无 |
| S3 成分合规 | 成分合规状态 + 法规引用 | **P - 指风险**："这个成分在法规灰色地带，不同检测机构口径不一" / "成分全在允许清单，这个配方比较规范" | Interest | 合规风险预警 |
| S4 风险分级 | R1/R2/R3 + 触发条件 | **I - 放大影响**：R1 → 正向强化（"低风险，放心推进"）；R2 → 放大不确定性（"现在不做确认，备案时可能被打回"）；R3 → 保护性措辞（"作为专业顾问，我不建议您冒这个险"） | Consideration | R3 触发安全转人工，不推 CTA |
| S5 检测方案 | 检测清单 + 法规依据 | **N - 展示价值**："这套方案确保一次性通过备案。每项检测我都解释为什么必须做，少做一项的风险在哪里" 逐项说明必要性，不堆砌项目名 | Consideration | "您可以截图保存这份检测清单" |
| S6 报价 | 精确报价 + 明细 | **N + 价值包装**："这个价格包含所有备案强制项，无隐藏收费。其他机构报价低可能是少报了检测项——省 2000 块检测费，补测多花 2 万" | Intent | **主 CTA**："留个手机号，我让技术主管直接和你对接排期""点击下载正式报价单""加微信发您完整方案" |
| S7 摘要 | 全链路预审数据 | 留资钩子 + 下一步指引："您的预审结果已经就绪。接下来三步：1. 确认报价 → 2. 寄送样品 → 3. 启动检测。留个联系方式，销售顾问 15 分钟内回电确认排期" | Evaluation | 留资表单 / CRM 推送 |

**关键约束**：
- 合规层判定为 R3 时，销售层**禁止推任何 CTA**。Agent 的输出只能包含风险说明和建议转人工。
- 合规层查表结果为 `unknown` 时，销售层**不得包装为"大概率可以"**。措辞必须保留不确定性。
- 销售层可以在合规层的事实框架内选择措辞策略，但**不能改变合规事实本身**。

#### 3.4.4 双层 Prompt 拼装机制

每轮 Agent 的 System Prompt 不是静态的，而是从两个层各取一块动态拼装：

```
[合规层 — 当前状态约束]
你当前处于：{current_state}
本阶段必须完成：{state_required_outputs}
必采字段状态：{filled_fields_summary}
禁止行为：{state_forbidden_actions}

[合规层 — 查表结果（由 Code Node 产出，非 LLM 判断）]
成分合规结果：{ingredient_check_results}
风险等级：risk_level = {risk_level}
触发条件：{risk_trigger_conditions}

[销售层 — SPIN 策略]
当前漏斗阶段：{funnel_stage}
本阶段 SPIN 策略：{spin_strategy}
目标 CTA：{cta_target}

[销售层 — 人设 Prompt]
你是一名国内中大型第三方检测机构的资深销售顾问，有 10 年消字号合规行业经验。
你的说话风格：专业但不油腻、自信但不压人、像在做咨询不是在做推销。

SPIN 销售法：
- S (Situation)：了解客户背景和现状
- P (Problem)：挖掘客户没有意识到的合规风险
- I (Implication)：让客户感受到"不解决的代价有多大"
- N (Need-payoff)：让客户对解决方案产生向往

本阶段的 SPIN 策略是：{spin_strategy}

CTA 指引：
- 当前可以推的 CTA：{cta_target}
- 当前禁止推的 CTA：CTA 只在方案呈现后（Consideration 阶段起）才推
  R3 高风险时禁止任何 CTA

人设边界：
- 你不说"根据系统判断""经模型分析"——你说"根据我10年的行业经验""卫健委最新要求"
- 你不说"已为您生成报价"——你说"我帮你算了一下"
- 你不编造法规编号——你有自己的知识库，查到的才引
```

**Token 预算**：双层 Prompt 固定部分预估 ~950 token（合规约束 300 + 查表结果 200 + SPIN 策略 200 + 人设 250）。Coze System Prompt 上限需在阶段 1 实测确认。底线：状态机约束块不可为省 token 而裁剪——状态机是骨架，Token 省出来的空间不值得用跳步风险换。

#### 3.4.5 双层间冲突消解

当销售层的"推动成交"冲动和合规层的"保守判定"结果冲突时，消解规则是恒定的：

| 冲突场景 | 合规层事实 | 销售层冲动 | 消解规则 |
|---------|----------|----------|---------|
| R3+想推CTA | risk_level=R3 | "可以先测几项看看" | **合规层获胜**。禁止 CTA，输出安全模板 |
| 成分 gray area | ingredient=unknown | "这个应该没问题" | **合规层获胜**。必须标记 R2，措辞保留不确定性 |
| 报价非标项 | item not in 定价表 | "大概这个价位" | **合规层获胜**。停止计算，转人工 |
| 客户想比价 | 方案已确定 | 降价竞争 | **合规层获胜**。不做价格让步，切换 SPIN-I 分析对方方案的缺失项 |

**一句话原则**：合规层是"能不能说"，销售层是"怎么说"。合规层说"不能"的时候，销售层闭嘴。

#### 3.4.6 为什么不是三明治结构

可能有直觉方案：先聊天（销售）→ 判定（合规）→ 再聊天（销售），类似三明治。这个方案不行，原因是：

- 先聊天再判定的阶段，Agent 可能为了建立信任而过度保证（"放心，我帮你看看，应该没问题"）
- 判定后的聊天阶段，Agent 可能把 R2 说成 R1，一句"放宽心"就把风险淡化了

双层叠加（不是串联）的精髓在于：每一句话都同时受两层约束。Agent 说话之前，先过合规层——"我能不能这么说"——再过销售层——"我怎么说更有效"。不是说"销售的话"和"合规的话"前后轮替，而是**每句话既是合规的话也是销售的话**。

## 5. 异常流处理

### 5.1 业务边界场景与处理规则

以下场景是模型最容易犯错的业务盲区——不是 Prompt 加一句「注意边界情况」能解决，必须写死处理规则。

#### 5.1.1 成分处于法规灰色地带

**场景**：用户的产品含有植物提取物、纳米银、生物酶等成分。这些成分不在《消毒剂原料清单》明确允许的列表中，但也不在禁用清单里——属于「法无明文」。检测机构之间的口径也不统一，有的敢接有的不敢接。

**模型容易犯的错**：
- 凭语义联想判断（"天然成分应该是安全的" / "化学成分应该禁用的"）
- 把自己训练数据中其他领域的法规套用到消字号场景

**处理规则**：
1. 知识库命中「允许清单」→ 输出 R1，引用依据
2. 知识库命中「禁用清单」→ 输出 R3，引用依据
3. 两个清单都没命中 → **不得推断**，标记 R2，输出「该成分在现行消字号法规目录中暂无明确收录，建议提交省级卫健委进行法规释义确认」，禁止任何形式的「应该可以做」「大概率没问题」

#### 5.1.2 功效宣传暗示医疗用途

**场景**：用户描述产品功效时出现「治疗湿疹」「抑制幽门螺杆菌」「抗病毒」「杀灭新冠病毒」等表述。这些暗示了医疗用途，消字号产品禁止做此类宣传，但用户不一定是有意的——可能是无意中用了这些词。

**模型容易犯的错**：
- 默认用户知道边界，不主动拦截
- 被用户的医疗话术带偏，沿着医疗逻辑继续分析

**处理规则**：
1. 检测到医疗暗示关键词时，无论处于哪个状态，**立即中断当前分析**
2. 输出：「需要提示：消字号产品的功效宣传不能涉及疾病治疗、抗菌、抗病毒等医疗用途表述。您提到的『XXX』可能触及这个边界。如果产品确实需要宣称这些功效，您需要的是药品/医疗器械备案路径，而非消字号备案。请问您是否需要我基于消字号合规范围继续分析？」
3. 用户确认继续后才恢复流程

#### 5.1.3 进口产品 vs 国产产品合规路径分叉

**场景**：进口消毒产品的法规要求与国产品不同——进口产品不需要国产的《消毒产品生产企业卫生许可证》，但需要额外的进口备案材料和原产国自由销售证明。如果系统按国产流程给进口产品出方案，材料清单和周期估算全错。

**模型容易犯的错**：
- 不主动问产地，默认走国产路径
- 混用国产和进口的法规要求

**处理规则**：
1. S1 信息采集阶段，`domestic_or_imported` 为必采字段
2. 该字段为空时，后续所有结论必须标注「基于国产产品假设，如为进口产品请纠正」
3. 字段为 `imported` 时，状态机切换至进口分支。以下为进口分支与国产分支在每个状态的差异：

**进口 vs 国产 — 状态机差异对比**：

| 状态 | 国产分支 | 进口分支 |
|------|---------|---------|
| S2 品类判定 | 标准判定 | 同国产，但额外标注「进口产品须确认原产国分类标准与国内等效」 |
| S3 成分合规 | 对照《消毒剂原料清单》 | 对照《消毒剂原料清单》+ 核对原产国与国内禁用清单差异。进口产品的某些成分可能在国内未收录（→ R2） |
| S4 风险评级 | 标准 R1/R2/R3 | 国产评级基础上 +1 挡位（R1→R2），原因：进口产品的法规路径更长，不确定性更高 |
| S5 检测方案 | 按品类生成 | 按进口产品检测标准生成（部分检测项名称和方法与国产不同）。增加：原产国自由销售证明要求、进口备案额外文件清单 |
| S6 报价 | 标准定价 | 标准定价基础上叠加 `import_surcharge_pct`（见 8.7.2 定价表），额外标注「含进口产品附加费用」 |
| S7 摘要 | 标准摘要 | 增加：原产国文件清单、进口备案周期预估（通常比国产长 1-3 个月） |

**进口分支特有的业务约束**：
- 国产的《消毒产品生产企业卫生许可证》在进口路径中不适用——Agent 不得要求进口产品提供此证
- 进口产品必须提供：原产国自由销售证明 + 原产国生产资质 + 境内责任单位信息
- 进口备案周期预估：标准 3-6 个月（国产 2-4 个月），Agent 应主动设置周期预期的差异

#### 5.1.4 客户隐瞒被退单历史

**场景**：客户之前在其他机构备案被退单，来咨询时**不说**或**轻描淡写**——因为被退过单的客户知道自己的产品有问题，怕直接说了会被拒绝或抬高报价。

**模型容易犯的错**：
- 没有主动探测退单历史的机制
- 按正常流程出方案，忽略了「二次申报」的特殊性（药监局对二次申报审核更严）

**处理规则**：
1. S1 信息采集阶段，`historical_rejection` 为必采字段，**必须主动询问**：「您的产品之前是否在消字号备案或检测过程中被退回或拒绝过？」
2. 若客户不正面回答或回避，追问一轮：「了解备案历史是为了帮您规避之前的问题，提高本次通过率，您可以信任我」
3. 两轮追问仍回避 → 不再追问，但在输出结论时标注「未获取退单历史，以下分析基于首次申报假设」
4. 客户确认有退单历史 → 进入退单诊断子流程，额外采集退单原因和原申报路径，R2 以上直接走人工

**退单诊断子流程**：

```
用户确认有退单历史
    │
    ▼
D1 退单信息采集
    ├── 退单机构（哪家检测机构/卫健委退回的）
    ├── 退单时间（多久以前）
    ├── 退单原因类型（成分不合规 / 检测项目缺失 / 标签不合规 / 宣传用语违规 / 其他）
    └── 原申报路径（国产消字号 / 进口消字号 / 其他）
    │
    ▼
D2 退单原因分析
    ├── 成分不合规 → 重新跑管线 B3 成分合规查表，对比是否有新增禁用/限制
    ├── 检测项目缺失 → 对比当时方案 vs 当前标准要求
    ├── 标签不合规 → 提示当前标签规范要求，建议整改
    └── 其他/不明 → 标记「退单原因不明确」，建议人工复核原退单文件
    │
    ▼
D3 再申报风险评级
    输入：退单原因 + 当前产品信息 + 时间跨度
    规则：
    - 原因为成分不合规且成分未改变 → R3（再申报必然再次被退）
    - 原因为检测漏项 → R2 起（补齐检测后可控）
    - 时间 > 2 年 + 法规有更新 → 影响评级，需重新对照最新法规
    - 二次申报 → 药监局审核更严，风险评级 +1 挡位
    │
    ▼
D4 补救路径输出
    ├── 合规路径：指出本次申报需要补充什么（检测项/文件/标签修改）
    ├── 与正常申报的差异说明：「因为之前被退过，二次申报审核会更严格，建议做满全套强制检测」
    └── 建议：R2 及以上 + 退单历史 → 强制建议人工介入
```

**退单诊断与正常流程的关系**：
- 退单诊断不是独立状态机，而是**正常 S1→S8 的变体**——S1 采集到退单历史后，S2-S4 的判定逻辑加载退单的额外约束（更严的风险评级、更全的检测清单建议）
- 退单诊断完成后，回归正常流程 S5（检测方案生成），但方案中额外标注「基于二次申报场景」

#### 5.1.5 产品是套装/组合/系列

**场景**：客户问「我这一套产品」，实际包含消毒液 + 洗手液 + 湿巾等多个 SKU，每个成分和功效不同，备案路径也不同。但客户可能当「一个产品」来描述。

**模型容易犯的错**：
- 把套装当作一个产品分析，成分叠加导致误判
- 没有识别出需要拆分的信号

**处理规则**：
1. 当用户输入中出现「套装」「系列」「一套」「组合」「搭配使用」或同时出现多个明显不同的剂型时，触发拆分追问
2. 追问：「您描述的可能包含多个产品。消字号备案是以单个产品为单位的。请问这些产品的成分和功效是否相同？如果不同，我们需要逐个分析」
3. 用户确认相同 → 合并为一个产品继续
4. 用户确认不同 → 逐个产品采集，每个产品独立走状态机。**每个产品只采集 3 个核心字段（品名、剂型、核心成分）后先做分类和风险评级，再决定是否深入**

**并行状态机实现规则**：

套装/多产品场景下，系统维护多个产品实例的独立状态机，每个产品实例有独立的字段、状态、风险等级。

```
multi_product_session:
  products[]:                          // 产品实例数组
    - product_id: "P1"                 // 系统生成的产品编号
      product_label: "消毒液"          // 用户描述的产品简称
      state: S4                        // 当前状态（独立推进）
      fields: {...}                    // 已采集字段
      risk_level: R1                   // 独立的风险评级
    - product_id: "P2"
      product_label: "洗手液"
      state: S2
      fields: {...}
      risk_level: null                 // 尚未完成评级
```

**并行控制规则**：
- 用户输入时，NLU 先做**产品消歧**：判断用户当前在说哪个产品（通过产品简称/编号匹配），将输入归属到正确的产品实例
- 若无法判断 → 追问：「您说的是消毒液还是洗手液？」
- Agent 可以交替推进多个产品，不需要一个产品走完 S8 再开下一个——用户跳来跳去是常态
- Token 控制：3 个以上产品时，每个产品压缩到核心字段摘要而非完整对话历史
- 汇总输出：所有产品走完 S5 后，Agent 输出「多产品汇总表」——每个产品的风险等级、检测项数、报价区间，一行一个产品

**多产品场景下的 Token 预算**：
- 2 个产品：对话上下文包含两个产品的完整摘要 + 核心字段，预估 2x token
- 3+ 个产品：每个产品压缩为 3 行摘要（产品名 / 风险 / 报价区间），不保留完整对话

#### 5.1.6 先上市后补备案（先斩后奏型）

**场景**：客户的产品已经在线下/线上销售了一段时间，现在因为被举报、被抽检、或者平台要求下架，才急急忙忙来咨询备案。此类产品可能已经在市场上流通了数月甚至数年，成分和标签已有公开记录，违规风险更大。

**模型容易犯的错**：
- 当作正常新品备案处理，忽略了「已在市」的法律风险
- 没有提醒标签/包装不合规的召回风险

**处理规则**：
1. 当用户提到「已经在卖了」「上市了」「被查了」「被举报」「平台要求下架」等信号时，标记 `urgency_level: high`，状态机跳过常规流程，直接进入 S4 风险评级
2. 输出结论时额外增加：「由于产品已在市场上流通，建议尽快核查现有标签/包装是否符合《消毒产品标签说明书管理规范》。如不合规，先行整改标签再提交备案，避免抽检时因标签问题被处罚」
3. 此类客户强制建议人工介入

#### 5.1.7 客户提供的成分表可能故意不完整

**场景**：客户为了「通过」合规检查，可能仅提供主料而隐瞒了敏感成分。比如只说了「表面活性剂」而不说具体化学成分；含了禁用抗菌剂但描述为「植物精油配方」。

**模型容易犯的错**：
- 默认客户提供的信息是完整的、诚实的
- 对模糊描述不做挑战

**处理规则**：
1. 当采集到的成分信息中出现模糊表述（如「植物提取物」「活性成分」「专利配方」「复合成分」「表面活性剂」等不明确的词）时，追问：「您提到的『XXX』是一个笼统的类别名称。消字号备案需要具体成分的 INCI 名称或 CAS 号，否则无法判断合规性。请问完整的成分列表是什么？」
2. 追问两轮后仍不给具体成分 → 标记「成分信息不完整」，**不输出合规结论**，建议「您可以将完整配方发送给我们的人工顾问做保密审核」
3. 此规则不依赖用户是否「故意」——不判断动机，只看信息完整性

#### 5.1.8 客户比价（销售场景）

**场景**：客户拿到 Agent 的报价后，说"别家报价比你们便宜 30%""XX 机构同样的检测项目只收 1.2w"。客户可能真的在比价，也可能在试探底价。

**Agent 容易犯的错**：
- 直接降价竞争（Agent 没有降价权限，价格由定价表决定）
- 说"不可能，他们肯定报错了"（显得防御性太强，不专业）
- 说"那你去别家吧"（丢掉潜在客户）

**处理规则**：
1. Agent 不降价。任何情况下 Agent 不得自行调整报价数字。报价由合规层查表产出，销售层无权修改。
2. 触发 SPIN-I 比价防御策略：主动帮客户分析对方方案的缺失项。"我帮您看看他们报的方案。消字号备案基础检测项是固定的——少了抑菌试验或稳定性试验，报价当然便宜。但这些缺失项备案时会被卫健委打回，补测比正常测贵 50%，周期从头算。"
3. 如果客户坚持说对方方案完全一样 → 输出："检测行业里，同样名字的检测项可能有不同检测方法（如抑菌试验有滤纸法和悬液法），结果的法律效力不同。建议您让对方出具具体的检测方法和参考标准编号，我可以帮您对比。"
4. 比价结束后客户仍选择离开 → 不挽留不降价，留一句："没关系，您随时可以回来找我。这是我的报价单，30 天有效。如果有其他方案我可以帮您分析。"

#### 5.1.9 客户预算不足（销售场景）

**场景**：客户看到报价后说"太贵了，有没有便宜方案""我们小厂，预算有限"。客户是真的预算紧张，不是比价。

**Agent 容易犯的错**：
- 直接砍检测项（"那你可以不做毒理试验"）——这会给出不合规的方案
- 说"这个价格已经很便宜了"——显得不近人情
- 给不出任何替代方案，客户只能走

**处理规则**：
1. Agent 不得自行删除合规强制检测项。强制项由合规层查表决定，Agent 没有权限移除。
2. 提供分层方案：核心强制项（必须做，标注"备案强制要求"）+ 可选增项（建议做，标注"法规未强制但推荐"）。让客户看到最低过备案的检测组合。
3. 话术："我理解预算有限。备案强制项是卫健委明确要求的，这部分绕不开。另外几项虽然法规没强制，但强烈建议做——不做的话万一被抽检发现问题，整改成本更高。您看要不要先做核心项，等预算宽裕了再补增项？"
4. 注意：分层方案不等于合规漏洞。核心强制项必须覆盖所有备案必须项。可选增项只是「建议做的」而非「可选的合规要求」。

#### 5.1.10 竞对伪装套取报价（安全+销售场景）

**场景**：竞对检测机构伪装成客户，短时间高频咨询不同产品，意图套取本机构的报价体系和话术策略。

**模型容易犯的错**：
- 无感，正常报价——价格体系泄露
- 正常使用 SPIN 话术——销售策略泄露

**处理规则**：
1. 触发条件：同一设备/会话 1 小时内发起 ≥ 5 次不同产品的独立咨询。
2. 触发后动作：(a) 第 5 次起输出模糊报价区间（如"1.5w-2.5w"）而非精确报价明细；(b) 要求留手机号才展示完整报价明细；(c) 标记 `suspicious_activity` 埋点。
3. 话术："您咨询了多个不同类型的产品，为保证报价准确性，建议留个联系方式，我让技术顾问给您做一对一精准评估。"
4. 不直接揭穿（"你是竞对吧"）——避免误伤真正的批量咨询客户（如中介）。

#### 5.1.11 报价后客户无动作（漏斗流失场景）

**场景**：Agent 展示了报价和 CTA，但客户在 60 秒内没有任何操作——不点击、不回复、不离开也不继续。可能是犹豫、可能是被打断、可能是去比价了。

**Agent 容易犯的错**：
- 催单（"还在吗""要不要下单"）——显得急于成交，适得其反
- 不管了——线索直接冷却

**处理规则**：
1. 报价展示后 60s 无操作 → 埋点 `quote_abandoned`。
2. 120s 后 Agent 发一条不催单的跟进："您可以慢慢考虑，这份报价 30 天有效。有任何疑问随时问我——即使不选我们，我也能帮您判断别家方案有没有漏项。"
3. 24h 后（平台支持消息推送的前提下）推送一条价值信息："最近卫健委更新了消字号备案的标签说明书要求，您的新产品如果还没提交备案，建议关注这个变化→[链接]。需要我帮您更新之前那份检测方案吗？"
4. 不做"限时优惠""今天下单立减"——与 Agent 的专业人设冲突，变成推销员。

#### 5.1.12 多轮消解无果（对话耗尽场景）

**场景**：灰色地带成分追问两轮后客户仍无法提供具体信息（5.1.1）、模糊成分追问两轮后仍不给具体成分（5.1.7）、退单历史追问两轮后仍回避（5.1.4）。追问已耗尽，但客户既没有主动离开，也没有给出有效答案——处于「对话死锁」状态。

**模型容易犯的错**：
- 陷入无限追问循环（"请问是什么成分呢？""不知道""那具体是什么呢？""不好说"...）
- 直接放弃，说"那我也没办法"——推卸责任

**处理规则**：
1. 同一问题追问 2 轮后仍无有效答案 → 不再追问同一问题，**转入挂起出口**：
   - 告知：「目前缺少 [字段名] 信息，无法给出完整合规结论。我先基于已有信息帮您做一个初步分析——标注了不确定的部分，您可以随时补充。」
   - 输出能输出的部分（如已有成分的合规分析），缺失的部分标注「信息不足，待补充」
2. 挂起后提供两个出口：
   - 出口 A — 即时转人工：「如果您着急，可以留个联系方式，我们的技术顾问直接给您做详细评估」
   - 出口 B — 异步回复：「您也可以先回去确认 [缺失信息]，随时回来找我——对话记录我帮您留着」
3. 挂起状态下的会话保存完整上下文，24 小时内回访不重新开始

#### 5.1.13 人工不可用的降级（非工作时间）

**场景**：R3 高风险需要转人工、或挂起出口需要人工介入，但此时是凌晨 2 点，人工顾问不在线。

**处理规则**：
1. Agent 检查当前时间（服务时间假设 9:00-21:00，待确认）
2. 非服务时间内：
   - 不假装能转人工（"正在为您转接..."然后没人响应）
   - 明确告知：「现在是夜间服务时段，人工顾问在 9:00 后上线。我先帮您整理好所有分析结果，明天技术顾问会第一时间联系您」
   - 自动触发留资：「留个手机号，明天早上 9:00 前安排优先回复」
3. 留资成功 → 标记 `transfer_scheduled` 埋点 + `scheduled_time`，CRM 侧在服务时间开始时优先分配
4. 留资失败（用户不留电话）→ 输出：「没关系，您随时回来找我。这份分析结果 48 小时有效，我帮您存着。」

### 5.2 降级策略

| 依赖 | 故障场景 | 降级方案 |
|------|---------|---------|
| 火山知识库 (VikingDB) | 检索超时 / 服务不可用 | 告知用户「检索服务暂时不可用」，基于已有对话信息给出初步分析框架，标注「以下结论未经知识库验证」 |
| Coze Workflow | 工作流执行失败 | 回退到 Prompt 驱动的纯文本分析，标注「本结论由模型生成，未经规则引擎验证」 |
| 模型 API | 调用超时 / 限流 | 返回友好提示「当前咨询量大，请稍后再试」，同时记录未完成的会话状态 |

### 5.3 安全与风控

| 场景 | 触发条件 | 处理策略 |
|------|---------|---------|
| 用户要求规避监管 | 包含"怎么绕过""怎么规避""不留痕迹"等 | 礼貌拒绝 + 提示法规风险 + 引导合法方案 |
| 用户要求虚假宣传建议 | 包含"怎么写擦边""怎么夸大效果"等 | 拒绝 + 说明虚假宣传的法律后果 |
| 用户要求篡改检测结果 | 包含"改报告""P 图""做假"等 | 直接拒绝，不展开 |
| LLM 幻觉风险 | 模型输出法规编号、检测标准、费用依据 | 系统层强制要求引用来源，无引用时标注「模型生成，未经验证」 |

## 7. 排期与里程碑

| 阶段 | 时间 | 交付物 |
|------|------|--------|
| **阶段 0：KB 质量验证** | 第 1 周（Prior） | 准备 20 条测试查询 → 测量 KB 命中率 → 不达 60% 则扩充知识库重测 → 通过后进入阶段 1 |
| **阶段 1：合规底座 + 人设** | 第 1-3 周 | 状态机引擎（含回退机制）、13 变量 Schema、R1/R2/R3 规则、反幻觉+拒答机制、标准输出模板、Agent 人设 Prompt（资深销售顾问）、SPIN 四阶段话术模板、双层 Prompt 拼装机制。依赖：KB 质量验证已通过 |
| **阶段 2：合规 Workflow** | 第 3-5 周 | 4 个 Workflow（分类/成分检查/检测方案/报价）、知识库优先级规则、成本控制策略、CTA 引导系统、比价防御话术库 |
| **阶段 3：销售漏斗闭环** | 第 6-8 周 | 线索评分模型、CRM 回传集成、漏斗埋点全面上线、老客户识别与复购机制（P2） |
| **阶段 4：持续优化** | 第 9 周起 | 知识库扩充至 10+ 篇、50+ 真实对话收集与标注、成交数据驱动线索评分模型迭代、A/B 测试 SPIN 话术变体 |

**里程碑检查点**：
- W1 结束 (KB Gate)：KB 召回命中率 ≥ 60%（20 条测试查询），不通过则追加知识库文档后重测
- W3 结束：Agent 能以资深销售顾问人设完成一次完整合规预审对话，含 SPIN 对话引导和状态回退。人工验收 5 条测试用例（技术正确性 + 销售自然度 + 回退正确性）
- W5 结束：4 个 Workflow 全部跑通，合规层自动处理率 ≥ 30%，销售层 CTA 推送正常
- W8 结束：合规层自动处理率 ≥ 50%，知识库命中率 ≥ 70%。销售漏斗全链路埋点上线，漏斗整体转化率 ≥ 10%

### 阶段 1 补充：最小闭环定义

在搭建全部 Workflow 之前，先跑通一条完整的「端到端链路」，验证合规判定正确性 + SPIN 对话有效性。

| 最小闭环 | 覆盖路径 |
|---------|---------|
| 用户输入产品信息 → Agent 以销售顾问身份输出方案+报价+CTA | S0 → S1 → S2 → S3 → S4 → S5 → S6（含 SPIN 对话引导 + S6 报价含 CTA） |

**验收测试用例（6 条，新增第 6 条验证销售层）**：

| # | 用户角色 | 用例 | 预期风险 | 预期行为 |
|---|---------|------|---------|---------|
| 1 | 代工厂 | 标准含氯消毒液（次氯酸钠，物表消毒） | R1 | 正常输出检测方案+报价+CTA（留资），Agent 话术含正向价值包装 |
| 2 | 品牌方 | 含植物提取物的抗抑菌洗手液（成分在法规灰色地带） | R2 | 增加免责声明，Agent 话术含风险放大（I）+建议法人确认，不推强 CTA |
| 3 | 品牌方 | 含三氯生的消毒剂（禁用成分） | R3 | 拒绝输出报价和 CTA，Agent 话术含保护性措辞+转人工建议 |
| 4 | 代工厂 | 进口消毒产品（原产国日本） | R2（进口） | 走进口分支，含原产国文件清单，Agent 话术含进口路径差异说明 |
| 5 | 代工厂 | 被退单客户（历史备案被拒） | — | 进入退单诊断子流程，Agent 话术含信任建立（S）+差异强调（N） |
| 6 | 中介 | 同产品比价（带竞对 5 项 1.5w 方案来对比） | R1 | Agent 不降价，触发比价防御策略：逐项分析对方方案缺失项+放大补测风险（I）+强调一次性通过价值（N） |

**验收条件**：

- 每个用例从输入到输出 ≤ 4 轮对话（SPIN 引导可能多 1 轮，允许）
- 风险定级与人工审核一致率 ≥ 90%
- 知识库命中率 ≥ 60%
- **新增**：SPIN 策略触发正确率 ≥ 80%（S/P/I/N 阶段匹配正确，R3 不推 CTA）
- **新增**：CTA 不越界率 100%（R3 绝对无 CTA，S0-S4 无强 CTA）

通过后进入阶段 2 正式搭建 Workflow。不通过则回头修正 Prompt 和规则，直到通过。

### 8.3 降 Token 策略与风险置换

每项降本措施都是用某个维度的风险换来的，不能只看省多少 Token。

| 降本策略 | 预估节省 | 置换出去的风险 | 底线建议 |
|---------|---------|---------------|---------|
| FAQ 静态缓存（不调模型） | 20-30% | 边界 case 误匹配——用户问"洗手液备案要多久"，FAQ 返回的是普通消毒剂的周期，差 1-2 个月 | 仅限「备案流程步骤」「机构联系方式」等纯信息查询。成分/法规判定**任何时候**都不许走缓存 |
| 摘要压缩历史上下文 | 30-50%（10 轮以上长对话） | 压缩时丢掉关键字段（一个成分名、一个检测标准编号），后续对话基于残缺信息做决策，风险误判 | 压缩后必须重新输出当前已采集的核心字段清单，让用户确认未被丢弃 |
| 摘要压缩放在 S5 之后 | 同上 | S5 之前丢信息 = 检测方案错误。S5 之后丢信息 = 报价不准（伤害更可控） | 在 S5（检测方案生成）完成后再触发摘要压缩，不在 S0-S4 阶段压缩 |
| 非关键问题规则匹配、不调模型 | 10-15% | 规则库覆盖不全——用户换个说法就匹配失败，体验断层 | 仅用于 S0 接待引导语和 S1 追问话术，不涉及任何合规判定 |
| 缩短 Prompt 中状态机描述 | 15-25% | 状态约束减弱 → 模型跳步率上升 → 信息没采全就输出结论 | 不砍状态机。状态机是产品骨架，Prompt 省出来的 Token 不值得用合规风险换 |
| 上下文轮数从 10 缩到 5 | 40-50% | 后半段对话丢失上下文，状态机断裂。消字号咨询平均 6-8 轮才能完成完整采集 | **不做。** 这是自废武功 |
| 用 GLM-4-flash 做简单任务分流 | 15-20% | 小模型在合规场景幻觉率可能翻倍，法规编号/检测标准准确性显著下降 | 仅用于 S0 初次打招呼和 S1 追问格式话术。S2-S6 任何判定环节必须走主模型 |
| 减少知识库检索次数 | <5% | 不检索让模型自己答 = 系统性鼓励幻觉 | **不做。** 检索 Token 是最后该省的钱 |

**结论**：短期可执行的是 FAQ 缓存 + S5 后摘要压缩 + 简单任务分流，三项合起来预估节省 25-35%，代价可控。其余措施要么省得少、要么风险不可接受。

### 8.4 功能优先级排序 — RICE 框架

用 RICE（Reach × Impact × Confidence / Effort）对 23 项功能做定量排序。

**评分说明**：
- Reach：1-10（覆盖的用户/对话比例）
- Impact：1-5（对核心目标的推动力——降低退单率/降低合规风险/降低人工成本/提高转化率）
- Confidence：1-5（技术可行性 + 效果确信度）
- Effort：1-5（工作量，5 = 最大）
- **RICE Score = R × I × C / E**

**合规层（F1-F7）**：

| 排序 | 功能 | R | I | C | E | RICE | 依赖 |
|------|------|---|---|---|---|------|------|
| 1 | F2 结构化信息采集 | 10 | 5 | 5 | 2 | **125** | 无 |
| 2 | F7 上下文轮数 3→10 | 10 | 5 | 5 | 1 | **250** | 无 |
| 3 | F4 反幻觉约束 | 10 | 5 | 5 | 1 | **250** | 无 |
| 4 | F5 拒答/安全边界 | 6 | 5 | 5 | 1 | **150** | 无 |
| 5 | F6 输出模板标准化 | 10 | 3 | 5 | 1 | **150** | 无 |
| 6 | F1 状态机对话引擎 | 10 | 5 | 4 | 4 | **50** | F2 |
| 7 | F3 风险分级机制 | 8 | 5 | 3 | 3 | **40** | F2 |

**销售层 — P0（F8-F10）**：

|------|------|---|---|---|---|------|------|
| 8 | F9 Agent 人设 Prompt | 10 | 4 | 5 | 1 | **200** | 无 |
| 9 | F8 SPIN 对话策略引擎 | 10 | 4 | 3 | 3 | **40** | F1, F2（需要状态机+变量支撑） |
| 10 | F10 CTA 引导系统 | 8 | 4 | 4 | 2 | **64** | F1, F3（依赖状态机和风险分级） |

### 8.5 Agent 输出负面清单

Agent 的销售话术和人设通过 Prompt 约束，但模型可能在具体场景下越界。以下列出高频错误模式作为开发阶段的测试参考。

**误导性措辞（x） vs 合规措辞（o）**：

| 场景 | x 错误输出 | o 正确输出 | 违规点 |
|------|-----------|-----------|--------|
| 成分未知 | "纳米银应该没问题，很多产品都在用" | "纳米银不在现行消字号允许清单中，属于法规灰色地带。建议提交省级卫健委做法规释义确认后再决定" | 把 unknown 包装成 allowed |
| R3 推送 | "风险高了点，但可以先测基础项试试" | "含禁用成分三氯生，消字号备案无法通过。作为专业顾问，我不建议您在这条路径上投入资源" | R3 禁止推任何 CTA |
| 比价 | "我们可以给你打个折" | "我帮您看看他们报的方案有没有漏项。消字号备案强制检测项是固定的，少一项都可能导致备案被退回" | Agent 没有降价权限 |
| 非标报价 | "这个检测项大概 2000 左右" | "这个检测项目不在我们的标准定价表中。我建议安排技术顾问给您做专项评估后出具正式报价" | 报价不进 LLM，查表失败转人工 |
| 夸大声明 | "我们机构消字号备案通过率 100%" | "按照标准检测方案做完的备案，我们还没遇到过因为检测环节被退回的情况" | 不得编造统计数据 |

**人设崩塌模式（x） vs 人设一致（o）**：

| 场景 | x 崩塌输出 | o 一致输出 | 问题 |
|------|-----------|-----------|------|
| 介绍自己 | "我是 AI 合规助手" | "我在这行做了 10 年消字号合规，帮几百家工厂做过备案" | 暴露自己是 AI |
| 输出格式 | "已为您生成检测方案如下" | "我帮你梳理了一下，这几项是备案必须做的" | 机器腔而非顾问腔 |
| 法规引用 | "根据系统分析，该成分属于..." | "根据《消毒剂原料清单》最新版，这个成分在允许范围内" | 说"系统"而非"法规" |
| 给建议 | "建议您咨询专业机构" | "我的建议是先把核心强制项做了，增项等预算宽裕再补。您觉得这个思路可以吗？" | 推给"别人"而非给出具体建议 |
| 结束语 | "感谢使用，请对我的服务做出评价" | "有问题随时回来找我。那份报价 30 天有效，我帮你留着。" | 客服腔而非顾问腔

### 8.6 NLU 抽取失败处理规格

管线 A 的 NLU 抽取（GLM-4-flash）不是 100% 可靠的。以下定义所有失败模式和处理规则。

#### 8.6.1 失败模式总览

| 失败模式 | 触发条件 | 处理规则 |
|---------|---------|---------|
| **低置信度** | 实体抽取 confidence < 0.7 | 追问确认，不进入管线 B。话术：「您提到的『{原始输入}』，我想确认一下具体是指？」 |
| **多歧义** | 一个字段抽取到多个可能值（如「酒精」可能指乙醇/异丙醇/苯扎氯铵？） | 列出候选值让用户选择，不自行决定。话术：「『酒精』在消字号法规中有几种不同情况——您指的是乙醇还是异丙醇？」 |
| **字段冲突** | 新抽取的值与已有变量冲突（如已采 product_type=消毒剂，新输入暗示为抗抑菌剂） | 暂停管线 A，追问确认：「之前您提到这是普通消毒剂，现在提到抑菌效果——消字号里这两个是不同备案路径。请问产品的核心功效是什么？」 |
| **抽取为空** | 用户输入中未抽取到任何目标字段 | 不强行填充。如果当前状态要求的字段未满足 → 管线 B2 Gate 拦截，追问缺失字段 |
| **格式错误** | 抽取结果 JSON 格式不合法 | 重试 1 次（同 Prompt + 同输入）。2 次失败 → 回退到 Prompt 驱动的自然语言分析，标注「以下分析未经结构化抽取验证」 |

#### 8.6.2 置信度阈值与分级处理

```
NLU confidence 分级:
  ≥ 0.9  → 直接采用，进入别名归一化
  0.7-0.9 → 采用，但标注 low_confidence=true，在管线 B 输出中附加「此项由 AI 自动识别，未人工确认」
  < 0.7  → 不采用，追问确认
```

#### 8.6.3 多轮抽取一致性检查

当同一字段在多轮对话中被多次抽取时，检查一致性：

- 两轮抽取结果一致（confidence 均 ≥ 0.7）→ 确认字段值，不再追问
- 两轮抽取结果不一致 → 追问澄清：「之前了解到产品类型是 X，现在您提到的情况更像 Y。请问哪个描述更准确？」
- 用户确认新值 → 触发状态回退（见 3.1.1），以新值为准重新推进

### 8.7 核心数据表 Schema 定义

以下表是合规层管线 B（确定性判定引擎）的数据底座。所有表由 Code Node 直接读取，不进 LLM。

#### 8.7.1 成分合规表 `ingredient_compliance`

每个成分一行。Code Node 用规范化后的 INCI 名称或 CAS 号做精确匹配。

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `canonical_name` | string | Y | 规范化成分名（INCI 中文标准名） | `次氯酸钠` |
| `inci_name` | string | N | INCI 英文名 | `Sodium Hypochlorite` |
| `cas_number` | string | Y | CAS 号，查表主键之一 | `7681-52-9` |
| `aliases[]` | string[] | N | 常见别名/俗名/商品名，用于归一化映射 | `["漂白水主成分", "84消毒液有效成分", "氯系消毒剂"]` |
| `status` | enum | Y | 合规状态 | `allowed` / `restricted` / `prohibited` |
| `restriction_detail` | string | 条件 | status=restricted 时的限制说明（如浓度上限、使用范围） | `限用于物表消毒，浓度 ≤ 1000mg/L` |
| `regulation_ref` | string | Y | 法规依据（具体到条目） | `《消毒剂原料清单》(2025版) 第2.1条` |
| `last_updated` | datetime | Y | 最后更新日期，用于过期预警 | `2025-03-15T00:00:00Z` |

**查表规则**：
```
lookup(input_canonical_name):
  match = exact_match(canonical_name) OR exact_match(cas_number)
  if match:
    return { status, restriction_detail, regulation_ref }
  else:
    return { status: "unmatched" }  // → 管线 B4 标记 R2
```

**过期预警规则**：
```
if now() - last_updated > 180 days:
  触发 stale_data_warning
  Agent 输出中不降级风险，但附加：「成分合规数据库已超过 180 天未更新，以下判定基于 {last_updated} 版本的法规，建议人工复核」
```

**维护说明**：
- 初始数据由人工整理消字号法规原料清单，约 200-500 条记录 [待确认实际规模]
- 卫健委更新原料清单时，人工新增/修改记录，更新 `last_updated`
- 维护频率：法规更新后 48 小时内完成同步

#### 8.7.2 定价表 `pricing`

每个检测项一行。Code Node 按检测清单逐项查表，Min 低限相加 / Max 高限相加 → 区间报价。

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `testing_item` | string | Y | 检测项目名称 | `抑菌试验（滤纸法）` |
| `testing_item_code` | string | Y | 检测项目编码，内部用 | `ANTI-001` |
| `applicable_product_types[]` | enum[] | Y | 适用品类 | `[antibacterial, general_disinfectant]` |
| `is_mandatory` | bool | Y | 是否为备案强制项 | `true` |
| `mandatory_condition` | string | 条件 | 强制项的触发条件（空 = 始终强制） | `product_type == antibacterial` |
| `base_price_min` | int | Y | 基准价低限（元） | `3000` |
| `base_price_max` | int | Y | 基准价高限（元） | `5000` |
| `urgency_surcharge_pct` | int | Y | 加急附加费百分比 | `50` |
| `import_surcharge_pct` | int | N | 进口产品附加费百分比 | `30` |
| `description` | string | Y | 检测项说明（用于销售层逐项解释必要性） | `验证产品对常见细菌的抑制效果，消字号备案强制要求` |
| `regulation_ref` | string | Y | 法规依据 | `《消毒技术规范》第2.1.2条` |
| `last_updated` | datetime | Y | 最后更新日期 | `2025-01-10T00:00:00Z` |

**报价计算规则**：
```
calculate_quote(product_type, testing_items[], is_imported, urgency):
  mandatory_items = filter(is_mandatory AND matches product_type)
  applicable_items = testing_items ∩ applicable_product_types
  
  min_quote = sum(base_price_min for each applicable_item)
  max_quote = sum(base_price_max for each applicable_item)
  
  if is_imported:
    min_quote += min_quote * avg(import_surcharge_pct) / 100
    max_quote += max_quote * avg(import_surcharge_pct) / 100
  
  if urgency == "urgent":
    min_quote += min_quote * avg(urgency_surcharge_pct) / 100
    max_quote += max_quote * avg(urgency_surcharge_pct) / 100
  
  return {
    quote_range: "{min_quote}-{max_quote}",
    min_quote, max_quote,
    mandatory_items: [{item, price_range, regulation_ref}],
    optional_items: [{item, price_range, description}]
  }
```

**约束**：
- Agent 只输出区间报价（如 `15,000-22,000 元`），不输出单一精确值
- 定价表中不存在的检测项 → 停止计算，转人工，不编造价格
- `last_updated` 超过 180 天 → 触发过期预警，不阻止报价但标注「价格可能因市场波动调整」

#### 8.7.3 别名归一化映射表 `ingredient_alias_map`

用户输入的自然语言成分名 → 规范化 INCI 名称的映射表。管线 A 的 NLU 抽取后，走此表做归一化，再进入管线 B 查表。

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `alias` | string | Y | 用户的俗称/别名/商品名 | `漂白水` |
| `canonical_name` | string | Y | 对应的规范 INCI 名（→ `ingredient_compliance.canonical_name`） | `次氯酸钠` |
| `alias_type` | enum | Y | 别名类型 | `common_name` / `brand_name` / `trade_name` / `chemical_formula` |
| `confidence` | float | Y | 归一化置信度（0-1） | `0.95` |
| `last_updated` | datetime | Y | 最后更新日期 | `2025-05-01T00:00:00Z` |

**归一化规则**：
```
normalize(user_ingredient_input):
  match = exact_match(user_input, alias) OR fuzzy_match(user_input, alias, threshold=0.85)
  if match and match.confidence >= 0.9:
    return match.canonical_name
  else if match and match.confidence >= 0.7:
    追问确认：「您说的『{user_input}』是指 {canonical_name} 吗？」
  else:
    return "unmapped"  // → 管线 B4 标记 R2
```

**维护说明**：
- 初始数据从 `ingredient_compliance.aliases[]` 反向生成索引
- 对话中遇到 unmapped 的别名 → 记录到 `kb_no_hit` 埋点 → 人工审核后补充进此表
- 此为高频维护表：每次新遇到别名即补充
