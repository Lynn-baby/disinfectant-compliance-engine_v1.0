## 一、已完成的诊断与修改（4 项 ✅）

### 1.1 识别了原报告的核心架构遗漏

**发现**：原报告在六（推荐技术路线）中默认接受了"知识库=向量检索"的前提，未质疑向量检索是否适合消字号合规场景。这个遗漏是根因级别的——RAG 检索质量是所有上层架构（状态机、风险分级、Function Calling）的地基。

**产出**：完整论述了三个遗漏维度：
- 未区分"检索错误"和"生成幻觉"两个独立风险源
- 未质疑向量检索在合规场景的适用性
- 未参考法律/法规领域的检索最佳实践

### 1.2 调研了法律判例系统的精确检索方案

**北大法宝（国内参考）**：
- MCP 平台将检索拆为 5 个独立服务：关键词精搜、语义泛搜、法条精准定位、法条溯源、AI 幻觉修正
- 核心启示：合规 AI 的共识是"语义检索 + LLM 生成之后，必须再加一层精确校验"
- "修正生成幻觉-法条"服务可直接迁移到消字号场景（生成后校验：输出的标准号/条文号是否真实存在于 KB）

**国际法律检索系统（Westlaw / COLIEE）**：
- 共识架构：两阶段级联管道（并行双路检索 → RRF 融合 → Cross-Encoder 重排）
- 关键数据点：巴西最高法院 (STJ) 实验证明 BM25 在法规条文精确匹配上**优于**纯 Embedding 模型
- COLIEE 2025 SIL 框架：BM25 + Doc2Vec 混合特征 + LightGBM 重排序 = 最高精度

### 1.3 推演了纯向量检索的 5 种具体失效模式

| # | 失效类型 | 触发场景 | 影响等级 |
|---|---------|---------|---------|
| 1 | 标准号混淆 | GB 15979-2024 vs GB 15979-2002，仅末四位不同，向量空间几乎重叠 | 高 |
| 2 | 条文号跳位 | 相邻条文语义高度相似，Top-K 语义排序 ≠ 条文号排序 | 极高 |
| 3 | 成分名称近似灾难 | "聚六亚甲基双胍盐酸盐" vs "聚六亚甲基胍盐酸盐"，不同化学物，向量分不清 | 极高 |
| 4 | 跨文档语义漂移 | 问毒理学检测，召回备案流程片段，精确片段被淹没在语义排序中 | 高 |
| 5 | 禁限用清单二元判定失败 | 成分合规是能/不能的精确判定，向量检索只能排序不能判定 | 极高 |

### 1.4 输出了路线图调整补丁

**文件**：`v1.0-diagnostic-patch_rag-retrieval.md`

**核心调整**：在 v2.0 原路线图的"阶段 1（基础重构）"之前，新增**阶段 0（检索基础设施重构，1 周）**：

| 新增任务 | 内容 |
|---------|------|
| R0 | 搭建混合检索引擎（BM25 关键词 + 向量语义，双路并行） |
| R1 | 建立结构化成分数据库（白名单/黑名单/限制清单，不走向量检索） |
| R2 | 建立检测标准号-版本索引（精确匹配用） |
| R3 | 定义查询分类规则（成分→关键词；泛化→向量；编号→精确匹配） |
| R4 | 实现检索结果的可溯源引用机制 |

**新增阶段 2 任务**：
| R5 | 实现生成后法规编号/标准号校验（参考北大法宝"修正生成幻觉"服务） |
| R6 | 实现结构化成分数据库的定期更新机制 |

**技术架构**：给出了三类查询的分治方案：
- 成分查询 → 结构化数据库（SQLite，不走 LLM）
- 法规编号/标准号 → 精确关键词索引（BM25/Boolean，不降级为向量兜底）
- 泛化咨询 → 混合检索（BM25 + 向量 + RRF 融合 + Cross-Encoder 重排）

**渐进式落地路径**：4 步最小可行方案，第一步当天可做（正则提取 + JSON 索引 + 20 行 Python）。

## 二、尚未落地的部分（7 项 ❌）

### 2.1 原报告本身未被修改

- **问题**：`v1.0-analysis-report_cc&gpt.md` 仍是 2026-05-18 的原始版本。补丁是独立新文件，不是对原报告的内联修改。
- **待办**：至少需要在原报告六（推荐技术路线）中增加一段 "已知局限"，标注向量检索不适合精确法规匹配，并引用补丁文件。
- **影响**：中。后来者只读原报告不会知道 RAG 层存在架构问题。

### 2.2 混合检索的 Coze 平台可行性未验证

- **问题**：补丁提出的混合检索架构（BM25 + 向量双路），Coze 平台能否落地？
  - Coze Workflow 能否发起 HTTP 请求调用外部 Meilisearch/Elasticsearch？
  - 如果能，双路检索 + RRF 融合的延迟是否在用户可接受范围（<3 秒）？
  - 如果不能，是否需要在 Coze 外部部署一个检索中间层 API？
- **影响**：致命。如果 Coze 平台不支持外部检索调用，整个阶段 0 方案需要重新设计。

### 2.3 结构化成分数据库的数据来源未确认

- **问题**：补丁 R1 要求建立"成分白名单/黑名单/限制清单"，但数据从哪里来？
  - 是否有官方发布的消字号成分清单？
  - 是否需要从《消毒技术规范》《化妆品安全技术规范》等法规中手工提取？
  - 初始录入规模预估（50-100 条高频成分）是否够覆盖 80% 的咨询场景？
- **影响**：致命。这是管线 B（确定性引擎）的数据底座，没有数据无法运行。

### 2.4 生成后校验层的误拦截风险未分析

- **问题**：补丁 4.3 节提出的"正则提取法规引用 → 精确索引校验 → 拦截不存在项"，存在：
  - **漏判**（false negative）：正则无法覆盖所有法规引用的写法（如"该规范第2.1.3条"省略了书名号）
  - **误判**（false positive）：知识库外的正确法规引用被拦截（用户的引用可能比 KB 更准确）
  - **边界**：校验失败后是静默拦截还是显式警告用户？前者可能丢失关键信息，后者体验差
- **影响**：高。校验层的设计缺陷可能比没有校验层更危险（过度拦截导致漏答）。

### 2.5 F0 的 20 条 KB 测试查询未撰写

- **问题**：与原 v2.0 PRD 检查点中的 2.4 相同。这 20 条查询是阶段 1 的前置门禁，当前未撰写。

### 2.6 知识库文档的结构化预处理未做

## 三、下一步需要思考的盲点（7 个维度）

### 3.1 Coze VikingDB 的能力边界

- 当前已知：VikingDB 在 Coze 中是"插件"形态，按 QPS 计费，只做向量检索。
- **盲点**：
  - VikingDB 的分块策略（当前 max_tokens: 1000，separator: \n）是否会切碎标准号/条文号？（如一条法规可能被切成 3 个分片）
  - VikingDB 的自定义 metadata 字段能否用于预过滤（如按"法规类型"过滤）？如果能，可以部分缓解精确检索问题。
  - VikingDB 和外部检索引擎能否在 Coze Workflow 中并联调用？还是互斥？

### 3.2 查询分类器的路由准确率

- 补丁 R3 定义了三类查询的路由规则：
  - 含标准号/法规编号 → 精确关键词
  - 含成分名称 → 结构化数据库
  - 其他 → 混合检索
- **盲点**：
  - 规则路由基于正则匹配，但真实用户输入往往不干净——"帮我看看15979里面微生物指标怎么规定的"（缺 GB 前缀），路由会漏判。
  - 成分名称和普通词汇没有明确边界——"酒精"既是成分也是日常词汇，路由该走哪条？
  - 是否需要一个小型分类模型（而非纯规则）做路由？

### 3.3 结构化成分数据库的维护可持续性

- **盲点**：
  - 消字号法规更新频率（新成分加入/旧成分调整/标准修订）→ 数据库多久需要更新一次？
  - 更新来源是什么？人工监控卫健委/药监局公告？还是用爬虫？
  - 如果数据库过期未更新，管线 B 会基于过时信息做判定——这比"不判定"更危险。**过期数据的危害 > 无数据**。
  - 需要定义数据库的 freshness SLA 和过期自动降级策略。

### 3.4 混合检索 vs. 纯向量检索的成本增量

- **盲点**：
  - 双路检索意味着每次查询调用两个检索引擎（VikingDB + Meilisearch），再跑 RRF 融合。4 篇文档的量级下延迟可忽略，但 10+ 篇、100+ 并发时呢？
  - Meilisearch/ES 的部署和运维成本（Docker 容器、内存、索引更新）
  - 对于单人开发者，Meilisearch + VikingDB + SQLite 三个数据存储的维护成本是否值得？有没有更轻的方案？（如 SQLite FTS5 替代 Meilisearch）

### 3.5 知识库文档的"精确检索友好"程度

- 当前 4 篇文档的结构未知，但补丁假设它们包含可提取的标准号、条文号。
- **盲点**：
  - 如果原文写的是"依据相关国家标准执行"而非"依据 GB 15979-2024"，精确索引就无从建起。
  - 需要对文档做"可检索性标注"——哪些段落可以被精确匹配？哪些段落只能语义理解？
  - 或许需要对知识库文档本身做一次"结构化改写"，在编写阶段就为精确检索埋下锚点。

### 3.6 成分合规判定的法律风险——"数据库说能用就真的能用吗"

- 补丁提出成分合规走结构化数据库，LLM 只做"翻译"不做"判定"。
- **盲点**：
  - 数据库是人工录入的，录入错误怎么办？数据库说"能用"但实际不能用，责任在谁？
  - 是否需要每个数据库条目标注"法规出处"作为可审计的决策依据？
  - 是否需要区分"明确允许""明确禁止""法规未提及"三种状态？（当前补丁只定义了 allowed/restricted/prohibited，缺 unknown）
  - unknown 状态的处理策略——告知用户"未在法规中找到" vs. 建议人工确认 vs. 静默通过？

### 3.7 v1.0 报告和 v2.0 PRD 的信息一致性

- **盲点**：
  - v2.0 PRD（消字号售前咨询v2.0-prd.md）是在 v1.0 报告的基础上写的，但它的 8.7 节已经包含了 `ingredient_compliance` 数据表 Schema（8 字段）和 `ingredient_alias_map`——说明 v2.0 PRD 的作者已经意识到结构化成分数据的必要性。
  - 但 v2.0 PRD 本身也没有质疑向量检索的适用性——它的管线 B（确定性引擎）的数据源假设是"已有成分数据表"，但没有说明这些数据表如何与 RAG 检索层协作。
  - **需要对齐**：v1.0 诊断补丁的"混合检索"结论，与 v2.0 PRD 的"三管线架构"之间的关系。检索层和管线层如何协作？还是补丁试图修正的问题在 PRD 中已经以另一种方式解决了？
