消字号合规预审引擎的 RAG 增强项目，定位为学习方法论（F级深度），而非纯功能开发。

## 学习目标

- **深度等级**: F — 形成可复用的方法论
- **核心研究问题**: 高相似度领域的近似实体消歧（次氯酸 vs 次氯酸钠，一字之差，法规要求完全不同）
- **领域**: 消字号法规体系（3-5份核心法规文档）
- **对标问题**: 为什么企业客服机器人的 RAG 很垃圾？从第一性原理拆解——电商 SKU 高相似度 + 传统 embedding 的语义压缩缺陷

## 已选路径：B — 工程渐进

先搭建带 best practice 的生产级 RAG，再把实体消歧做成可插拔模块，做 A/B 对比实验。

为什么不选 A（科学实验/baseline-first）或 C（基准驱动/先建 benchmark）：
- A 开头几周只有实验数据，速度感不足
- C 前期标注工作量大且枯燥
- B 快速出能用的系统 + 对比实验干净（唯一变量是消歧模块 on/off）

## 已确认的设计决策

### 整体架构
1. RAG 是附加服务，不替代现有 S0-S7 规则引擎 pipeline
2. 双模式设计：
   - **模式 A（优先做）**: 嵌入式法规溯源 — pipeline 检出问题后，RAG 检索对应法条，拼入报告
   - **模式 B（后做）**: 独立问答 Chat — `/api/chat` 端点，用户自由提问，LLM 生成带引用的回答
3. 先 A 后 B 的理由：A 专注验证检索准确性，B 的幻觉/对话管理会分散对核心问题（实体消歧）的注意力

### 技术选型
- **Embedding**: API 方案（Coze/智谱等），不本地跑 BGE，避开 M2 8GB 限制
- **向量库**: ChromaDB（本地、Python 原生、零配置）
- **分块策略**: 以"条"为单位 + 章标题作为上下文前缀
- **检索管线**: 查询改写+术语扩展 → 混合检索（语义+BM25）→ 重排序（Cross-encoder）→ 实体消歧 → Top-K
- **实体消歧**: 独立模块（`server/rag_entity_disambig.py`），可插拔，用于 A/B 对比

### 文件规划
- `server/rag_service.py` — RAG 全部逻辑（新建）
- `server/rag_entity_disambig.py` — 实体消歧独立模块（新建）
- `server/main.py` — 新增 /api/chat 端点 + 报告生成中调用 RAG（修改）
- `data/regulations/` — Markdown 格式法规原文（新建）
- `server/pipeline.py` — S0-S7 不改
